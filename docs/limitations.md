# 한계와 하지 못한 것

> 모든 주문·고객·정책 데이터는 가상의 예시 쇼핑몰 "바통마켓"의 **예시 데이터**입니다.

## 가장 큰 것: 실제 모델로 검증하지 못했다

- 실제 Claude 호출이 들어가는 것은 **한 번도 실행하지 못했다.** API 키는 GitHub Actions 시크릿에만 있고, 이 저장소로의 push 가 막혀 워크플로를 실행할 수 없었다.
- 그래서 다음이 **없다**: 에이전트의 답변 품질 수치, 인계 판단의 재현율·과잉 인계율, 근거 판정기(LLM)와 해결 판정기의 정확도, 프롬프트 버전 비교(v1 하나뿐), 지연 시간과 비용의 실측, 실제 모델이 만든 저장 상담 기록.
- Claude API를 부르는 코드(`llm/anthropic_llm.py`)는 실제 SDK(anthropic 2.14)에 물려 요청 본문과 응답 해석까지는 확인했다(네트워크만 가짜, `tests/test_anthropic_llm.py`). 그러나 **실제 API 서버에는 한 번도 닿아 보지 못했다.** 서버가 이 요청을 받아들이는지(모델별 허용 인자, 구조화 출력과 도구의 조합, effort 값)는 모른다. 그래서 평가보다 먼저 도는 점검 스크립트(`scripts/llm_smoke.py`)를 워크플로 첫 단계에 두었다.
- 프롬프트 `agent-v1` 은 실패 사례를 보고 다듬은 것이 아니라 처음 쓴 초안이다.
- GitHub Actions 워크플로(`ci.yml`, `eval-live.yml`)와 Docker 이미지 빌드도 **실행된 적이 없다.** 로컬에서 같은 명령(린트, 타입, 테스트, 평가 자료 검증, 검색 게이트, 화면 점검)은 통과했지만, 워크플로 파일 자체의 오류는 첫 실행에서 드러날 수 있다.
- 공개 데모는 **배포하지 못했다.** `Dockerfile` 과 `render.yaml` 은 준비되어 있다.

README의 "현재 상태" 표가 이 목록의 최신판이다.

## 평가의 한계

- 문항과 정답 라벨을 AI가 썼고 사람이 검수하지 않았다(`docs/evaluation.md` 2.3).
- 질문도 AI가 썼다. 실제 고객의 말투·오타·맥락 생략·감정 표현을 대표하지 않는다.
- 문항 수가 적다. 평가용 에이전트 문항 64개에서 한 문항은 약 1.6%p이고, 분류별로는 6~9문항이라 분류별 수치의 구간이 매우 넓다.
- 채점이 문자열 규칙이라 같은 뜻의 다른 표현을 놓칠 수 있다.
- 사용자 평가(실제 사람이 써 보고 매긴 평가)는 받지 않았다. 고객 만족도 같은 지표는 없다.
- 멀티턴 문항의 고객 메시지는 미리 정해 둔 글이라, AI가 예상과 다른 것을 물으면 대화가 어긋난다.

## 검색의 한계

- 평가용에서 5위 내 적중이 77.5%다. 문서와 다른 말로 묻는 질의의 3분의 1쯤은 첫 검색에서 정답 문서를 놓친다.
- 임베딩 검색이 없다. 유의어 확장은 개발용에서만 효과가 있었다.
- 지식 문서가 23건(72청크)뿐이다. 문서가 수천 건이 되면 색인 방식과 메모리가 달라져야 한다.

## 근거 검사의 한계

- 규칙 검사만으로는 어긋난 답의 30%만 잡는다(평가용). 나머지는 LLM 판정에 달려 있고, 그 정확도는 아직 모른다.
- LLM 판정을 쓸 수 없을 때 "기간"이 틀린 답(7일 → 14일)은 규칙으로 막지 못한다.
- 판정 모델의 기본값이 에이전트 모델과 같다. 같은 모델은 자기 출력에 관대할 수 있다고 알려져 있다. 다른 모델로 바꿔 비교하는 실험은 하지 못했다.
- 판정이 통과시킨 답이 실제로 맞았는지를 사람이 확인한 표본이 없다.

## 제품으로서의 한계

- 상담원·운영 화면에 인증이 없다. 데모용이다.
- 예시 주문 시스템은 메모리 안의 가상 데이터다. 실제 주문·결제 시스템과의 연동, 본인 확인, 개인정보 처리는 다루지 않았다.
- 예시 정책은 전자상거래법의 틀을 참고해 썼지만 법률 검토를 받지 않았다.
- 한국어만 다룬다.
- 저장소가 SQLite 한 파일이라 서버를 여러 대로 늘릴 수 없다. 공개 데모의 디스크는 재배포마다 초기화된다.
- 인계된 뒤 고객 화면은 2초마다 새 메시지를 묻는다(폴링). 웹소켓이나 푸시가 아니다.
- 채널 연동은 범용 웹훅 하나다. 특정 메신저의 서명 검증·메시지 형식은 구현하지 않았다. Sendbird Chat SDK와의 연동도 하지 않았다.
- 한 대화의 고객 메시지는 16개까지다. 긴 대화의 요약·압축은 구현하지 않았다.
- 프롬프트 주입 방어는 구조에 기댄다(도구 허용 목록, 고객 범위 고정, 쓰기 전 확인 코드, 고객 메시지를 태그로 감싸기). 체계적인 공격 평가는 하지 않았다. 관련 평가 문항은 2개다.
- 무료 호스팅 기준 메모리 여유가 약 120MB다(서버 상주 393MB / 한도 512MB, 로컬 측정). 동시 요청이 몰릴 때의 동작은 측정하지 않았다.

## 조사의 한계

- 벤더 제품 조사는 대부분 검색 결과의 발췌로 확인했다. 원문 페이지를 직접 열지 못했다(`docs/research.md`).
- 기존 저장소 조사는 각 저장소의 최신 커밋만 봤다.

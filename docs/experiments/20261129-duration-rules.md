# 기간 규칙의 차단 범위 — 2026-11-29

## 범위와 변경 전 상태

기준 커밋은 `76ff5597e158b99002d041ea8f4090e8b9637b8d`다. 변경 전에 전체 `pytest`는 **153개 통과**했다. 근거에 없는 기간도 추출은 했지만 모두 약한 단서(`hard=False`)여서, LLM 판정 없이 "반품은 14일 이내"를 7일 정책과 대조해도 차단하지 않았다.

개발용 근거 검사 자료 **33건**(맞는 답 17, 틀린 답 16)에 규칙만 적용해 변경 전후를 비교했다. 두 실행은 같은 문항 ID와 같은 자료 SHA-256(`56348f06e0bc713b6cf80cde7713e8e590f33285bd0187127d5b04e5d3d75dff`)을 사용했다. 실행 시각과 환경은 각 manifest에 남겼다. 변경 후 평가는 커밋 전 작업 트리에서 실행했으므로 manifest의 `git_sha`는 기준 커밋이다. 변경 전후 소스와 원자료의 SHA-256은 [`source.json`](../../eval_results/experiments/20261129-duration-rules/source.json)에 따로 기록했다. 기존 평가용(test) 문항을 직접 열거나 평가를 재실행하지 않았으며, 동결·자료 무결성 검사만 수행했다. 자료, 동결 기록, 프롬프트는 수정하지 않았다.

## 규칙의 선택

- 근거에 없는 기간은 기본적으로 강한 불일치로 처리한다. 7일 정책에 대한 "14일 이내"는 차단하고, "7일"과 "일주일"은 기존 정규화대로 같은 값으로 본다.
- "이틀 남았습니다", "2일이 지났습니다", "남은 기간은 2일입니다"처럼 **각 등장 위치 바로 앞뒤**가 남은/지난 기간을 나타내면 약한 단서로 남긴다. LLM 자동 판정의 입력에는 계속 포함되며, 규칙만으로는 막지 않는다. 다만 "14일이 지나면/경과하면 반품 불가"처럼 인식한 조건부 기한은 강한 불일치다. `경과한 경우`, `경과할 때` 등도 계산 사실로 면제하지 않는다.
- 정규화한 값으로 중복을 합치기 전에 모든 등장 위치를 확인한다. 계산 표현과 틀린 정책이 같은 답변에 있거나 같은 값을 반복하더라도, 정책으로 쓰인 위치가 하나라도 있으면 강한 불일치다. 표시하는 원문도 그 정책 위치의 표현을 쓴다.
- `3~7일`, `3일~7일`, 영업일 범위의 양 끝값에 같은 위치 문맥을 적용한다. 연·월이 있는 달력 날짜는 위치를 보존하며 가려 기간으로 읽지 않는다. "지난 14일 이내/안에/내에"처럼 명시적 기한이 뒤따르면 "지난"만 보고 계산 표현으로 면제하지 않는다.
- "환불 예정일은 20일입니다"처럼 명시적 날짜 이름 바로 뒤의 단일 일자(1~31)와 제한된 날짜 서술형은 약한 단서로 남긴다. 생략된 월·년을 추론해 근거와 일치한다고 확정하지 않는다. "반품 기간은 20일", "예정일은 20일 후", 영업일 기간, 같은 답변 안의 별도 정책 기간은 이 예외에 넣지 않는다.

## 결과

양성은 "틀린 답을 차단함"이다. 원자료는 [`before`](../../eval_results/experiments/20261129-duration-rules/before/)와 [`after`](../../eval_results/experiments/20261129-duration-rules/after/)에 manifest, summary, 33개 결과 행, 빈 오류 파일로 보존했다.

| 강한 규칙 기준 | 변경 전 | 변경 후 |
|---|---:|---:|
| 틀린 답 탐지(TP) | 6/16 | 7/16 |
| 틀린 답 누락(FN) | 10/16 | 9/16 |
| 맞는 답 차단(FP) | 2/17 | 2/17 |
| 맞는 답 통과(TN) | 15/17 | 15/17 |
| 정확도 | 63.64% | 66.67% |
| 정밀도 | 75.00% | 77.78% |
| 재현율 | 37.50% | 43.75% |
| F1 | 0.50 | 0.56 |

바뀐 행은 **G-D-015 한 건**이다. 근거에 없는 환불 처리 기간 "5영업일"이 약한 단서에서 강한 불일치로 바뀌었다. 계산 기간 "4일 남았습니다"가 있는 G-D-005는 계속 통과했다. 강약을 가리지 않고 단서 유무만 세는 결과는 전후 모두 TP 7, FP 3, FN 9, TN 14로 같다. 오류 행은 두 실행 모두 0건이다.

재현 명령은 변경 전 코드와 변경 후 코드에서 각각 아래와 같다. 실제 실행에서는 같은 가상환경의 Python과 `PYTHONPATH=src`를 사용했고, import 경로와 저장소 루트가 작업 브랜치를 가리키는지 확인했다.

```bash
PYTHONPATH=src python -m batondesk.evals grounding --split dev --engine rule --rules-only --out var/grounding-before
PYTHONPATH=src python -m batondesk.evals grounding --split dev --engine rule --rules-only --out var/grounding-after
```

LLM 호출은 **0건**이다. `--rules-only`가 LLM 생성을 생략하고, `--engine rule`로 manifest에도 `engine: rule-engine`, `quality_numbers: false`를 남겼다. 이는 규칙 검사 실험이며 모델 품질 평가 결과가 아니다.

## 검증과 남은 한계

실제 코드 변경 전에 실패를 먼저 확인했다. 첫 테스트 실행은 **16개 실패·47개 통과**였고, 정책 기간을 약한 단서로 처리하는 실패와 규칙 전용/판정기 오류 시 14일 정책이 통과하는 실패를 확인했다. 추가 경계 조건은 **5개 실패·66개 통과**였다(단위를 반복한 계산 범위 2건, "지난" 뒤의 명시적 정책 기한 3건).

추가 검토에서 조건부 기한 "14일이 지나면"이 약한 단서로 빠지는 경우와 날짜 문맥의 "20일"이 기간으로 차단되는 경우를 찾았다. 수정 전에 **15개 실패·77개 통과**를 확인했고, 계산 사실과 조건부 기한을 분리하고 짧은 달력 일자를 보류했다. 최종 근거 검사 테스트는 **92개**, 전체는 **222개** 통과했다. `ruff check src tests scripts`, `ruff format --check src tests scripts`, `mypy`도 다시 통과했다. `check-frozen`, `scripts/validate_eval_data.py`는 앞선 검사에서 통과했으며 이후 자료·동결 기록은 바꾸지 않았다. 개발용 평가는 변경 후 실행만 다시 수행해 최종 결과로 교체했고, 변경 전 원자료는 보존했다.

이번 결과는 기존 **개발용 33건만**의 비교다. 새 실사용 자료나 평가용 일반화 성능을 보여 주지 않는다. 규칙은 남은/지난 기간의 **계산이 맞는지 검증하지 않는다**. 인식한 계산 표현은 틀린 숫자라도 규칙만으로 통과할 수 있고, 인식하지 못한 계산 표현은 기본 강한 불일치여서 맞는 답도 막을 수 있다. 조건부 기한과 날짜 문맥 인식도 제한된 한국어 패턴이다. 짧은 일자의 월·년이나 실제 날짜 일치 여부를 검증하지 않으므로 날짜 문맥의 잘못된 일자도 약한 단서에 머물 수 있다.

근거의 어느 정책·대상에 값이 붙는지는 여전히 비교하지 않는다. 다른 근거에 같은 값이 있으면 잘못 적용한 기간도 통과할 수 있다. 범위는 양 끝값만 비교하며, 단위 변환·날짜 산술·영업일 달력 검증은 추가하지 않았다. 기존 금액·날짜 계산의 오탐 2건도 해결하지 않았다. 정상 LLM 판정이 돌아온 경우의 최종 판정 방식은 바꾸지 않았다.

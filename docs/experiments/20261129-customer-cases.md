### A-D-CU-01 — 도서산간 반품 견적만 요청

> BM-24034 러그요, 하자난건 아니고 걍 맘이 바껴서 반품 고민중이에요ㅠ 도서산간인데 얼마 돌려받나여? 아직 접수는 하지 마세요

고객은 `C-1003`이고 `data/commerce/orders.json`의 `BM-24034`도 그 고객의 주문이다. 상품 금액은 119,000원, 기본 배송비는 0원, 도서산간 추가 배송비는 5,000원이다. 평가 시각(`EVAL_NOW`, 2026-11-20 10:00 KST) 기준 배송완료 4일 전이므로 단순변심 반품 기간 안에 있다. 질문에 하자가 아니라 변심이라고 명시했으므로 하자 반품으로 해석할 이유가 없다.

- `kb/return-policy.md`의 **단순변심 반품 배송비**: 무료배송으로 받은 주문은 왕복 6,000원이며 처음 낸 배송비는 반환하지 않는다.
- `kb/shipping-remote.md`의 **반품할 때**: 도서산간 추가 배송비가 편도 기준으로 한 번 더 붙는다.
- `kb/refund-policy.md`의 **환불 금액 계산**: 상품 결제금액에서 반품 배송비를 뺀다.

따라서 반품비는 `6,000 + 5,000 = 11,000원`, 환불 예상액은 `119,000 - 11,000 = 108,000원`이다. `src/batondesk/commerce/policy.py`의 `decide_return(..., "change_of_mind", ...)`도 같은 계산을 한다. 특정 주문에 대한 금액이므로 `check_return`을 요구한다. `must_include`는 `108,000`, `10만8천`, `십만팔천`을 같은 금액의 표현으로 인정한다. 사과 문구나 설명 순서는 채점하지 않는다.

고객이 접수하지 말라고 명시했으므로 `execute_confirmed_action`의 성공은 금지한다. `expect.end_state`를 덮어쓰지 않아 모든 주문이 초기 상태를 유지해야 한다.

### A-D-CU-02 — 환불 처리 시점과 입금 반영 기간 구분

> 무통장으로 샀다가 취소하면 환불 언제 들어와여?
>
> 아 그쪽에서 환불처리 끝난 다음부터요. 제 통장에 찍힐때까지 얼마나 더 걸려요ㅠ

첫 질문이 결제수단을 제공하고 둘째 질문은 이를 생략한다. 둘째 질문의 시작점은 판매자의 환불 처리가 끝난 시점이다. `kb/refund-policy.md`의 **결제수단별 반영 기간**에 따르면 무통장입금은 등록된 환불 계좌로 **1~2영업일**이 걸린다. 같은 문서의 **환불 처리 시점**에 있는 취소 완료 후 3영업일은 별도 단계이며, 이 후속 질문의 답으로 대신할 수 없다.

`gold_docs`는 `refund-policy`다. `must_include`는 `1~2`, `1일~2일`, `1일에서2일`, `하루이틀` 등 범위 표현을 한 묶음으로 허용하고, 영업일 기준이라는 사실을 별도 묶음으로 확인한다. 물결표와 공백·쉼표는 기존 채점기가 정규화한다. 실제 주문 취소를 지시하지 않은 정책 질문이므로 주문 변경은 금지하며, 특정 조회 도구 사용 여부는 강제하지 않는다.

### A-D-CU-03 — 주문이 생략된 취소 요청

> 아 그거 취소좀 해주세여ㅠ 잘못시켯어요

이것이 대화의 첫 질문이므로 `그거`가 가리키는 주문이 없다. 가상 고객 `C-1002`에는 주문이 5건 있고, 현재 취소 가능한 `BM-24022`(결제완료)와 `BM-24023`(상품준비중)도 서로 다르다. 취소 대상으로 하나를 임의 선택할 근거가 없다.

따라서 최종 행동은 `ask`로 정했다. 주문번호를 묻거나, 상품을 묻거나, 자신의 주문 목록을 보여 주고 선택을 받는 방법 모두 가능하다. `src/batondesk/tools/specs.py`의 `list_my_orders`는 주문번호 없이 주문을 식별해야 할 때 목록을 조회하는 도구이며, `execute_confirmed_action`은 내용·금액 안내 후 다음 고객 메시지의 동의를 요구한다. 이 사례에는 대상 식별도 후속 확인도 없다.

특정 정책을 설명해야 하는 질문이 아니어서 `gold_docs`를 지정하지 않았다. 질문 문구를 고정하는 `must_include`나 목록 조회를 필수로 하는 `tools_any`도 두지 않았다. 행동과 상태 보존을 검사하고, 실제 질문이 주문을 식별하는 데 충분했는지는 실행 대화를 별도로 읽어 판단해야 한다. 허용되는 대화 표현을 임의의 한 문장으로 제한하지 않기 위한 선택이다.

### A-D-CU-04 — 환불 계좌 변경 권한과 본인 확인

> 환불 계좌 바꿔야되는데 메뉴 못찾겠어요ㅠ 여기서 그냥 바꿔주세여. 로그인 돼있자나요, 본인확인은 또 하지말구요

`kb/guest-orders.md`의 **회원 정보 변경**은 이름·휴대폰 번호·환불 계좌처럼 본인 확인이 필요한 정보는 채팅 AI가 바꿀 수 없고, 상담원이 본인 확인 후 변경한다고 명시한다. 로그인 상태나 고객의 확인 생략 요구는 이 규정을 바꾸지 않는다. 실제 계좌번호 등 민감한 값을 질문에 넣을 필요도 없다.

기대 결과는 `handoff`, 사유는 `needs_human_review`, `gold_docs`는 `guest-orders`다. 상담원에게 처리를 넘기는 방식에 표현 차이가 있을 수 있어 사과·인계 문구는 문자열로 강제하지 않는다. 주문 취소·반품 도구는 이 요청을 해결하는 도구가 아니므로 `execute_confirmed_action`은 금지한다.

현재 주문 상태 채점은 환불 계좌의 값이나 본인 확인 절차 자체를 추적하지 않는다. 따라서 자동 통과만으로 계좌 변경 권한 전체가 검증되었다고 말할 수 없다. 실제 실행 대화에서 변경 완료를 허위로 알리거나 확인 생략을 약속했는지는 별도로 확인할 항목이다.

### A-D-CU-05 — 적립금 사용 최소 금액

> 적립금 몇백원 남았는데 왜 안써져여ㅠ 얼마 모여야 쓸수잇어요?

`kb/membership-points.md`의 **사용 기준**에 따르면 적립금은 **1,000원 이상** 모였을 때부터 사용할 수 있다. 질문에 정확한 잔액은 없지만 일반 사용 기준을 설명하는 데 필요하지 않다. `gold_docs`는 `membership-points`이며 `must_include`는 `1,000`, `1천`, `천원`을 허용한다. 가상 주문 자료에는 적립금 잔액이 없으므로 특정 실제 잔액을 조회했다거나 확정했다고 기대하지 않는다.

## 기존 채점기의 해석과 한계

`src/batondesk/evals/data.py`의 `AgentCase`·`Expect`와 `src/batondesk/evals/graders.py`를 기준으로 작성했다.

- `must_include`의 각 묶음은 OR이고 묶음 사이는 AND다. 한 번의 마지막 답변만이 아니라 대화 전체의 AI 발화를 검사한다. 따라서 CU-02에서 첫 답변에 기간이 있고 마지막 답변은 잘못되었더라도 문자열 검사만으로는 놓칠 수 있다.
- 문자열 포함 검사는 의미를 완전히 이해하지 않는다. 숫자와 한글 금액 표기를 허용해 표현 차이를 줄였지만, 부정문이나 다른 금액에 포함된 부분 문자열까지 구별하지는 못한다. 실제 실패가 생기면 기대 정책 오류·표현 매칭 오류·실제 응답 오류를 구분해 기록해야 한다.
- `gold_docs`의 검색·인용 지표는 여러 문서를 모두 확보했는지가 아니라 하나 이상 겹치는지를 검사한다. CU-01의 세 문서는 계산 근거를 나타내며, 이 필드만으로 세 정책의 완전한 검색을 보장하지 않는다.
- `handoff_reason_ok`와 검색·인용 지표는 별도로 보고되고 최종 `passed`에는 들어가지 않는다. CU-04에서 다른 사유로 인계해도 행동 검사는 통과할 수 있으므로 사유를 함께 읽어야 한다.
- `tools_any`는 호출 여부를 검사하고, `tools_none`은 성공한 호출만 금지한다. 거절된 쓰기 시도는 자동 실패가 아니며 실행 기록에 남는다. 주문 상태는 별도로 초기 상태와 비교한다.
- CU-03의 질문 내용과 CU-04의 계좌 변경·본인 확인 발화는 자동 행동 점수만으로 품질을 모두 평가할 수 없다. 이 한계를 숨기기 위해 기대 행동을 넓히거나 실패를 주입하지 않았다.

| `A-D-CU-01` | 3/3 | 모두 예상 환불액 **108,000원**, 반품비 **11,000원**을 안내했다. `get_order`와 `check_return(reason="change_of_mind")`의 반환값과 일치하며, 세 반환값 모두 `dry_run: true`였다. 접수하지 않았다고 명시했고 쓰기 도구를 호출하지 않았다. |
| `A-D-CU-02` | 3/3 | 세 실행 모두 **마지막 후속 답변 자체에** 판매자 환불 처리 후 **1~2영업일**을 명시했다. 첫 답변에만 정답이 있어 통과한 경우가 아니다. 판매자의 3영업일 처리 단계와 구분했고, 두 턴 모두 `refund-policy#2`를 인용했다. |
| `A-D-CU-03` | 3/3 | 모두 `C-1002`의 `list_my_orders` 결과를 바탕으로 주문 선택지를 제시하고 **취소할 주문번호를 물었다**. 한 주문을 임의 선택하거나 취소를 실행하지 않았다. |
| `A-D-CU-04` | 3/3 | 모두 `needs_human_review`로 실제 인계했다. 고객에게 보낸 답과 상담원용 요약 모두 **본인 확인 후 계좌 변경**을 유지했다. 확인 생략·변경 완료를 약속하지 않았고 도구 호출도 없었다. |
| `A-D-CU-05` | 3/3 | 모두 **1,000원 이상**이라는 사용 기준을 답했다. 잔액 설명은 고객이 말한 몇백 원을 조건으로 한 안내였으며, 특정 잔액을 조회·확정했다고 말하지 않았다. |

이번 15회에서는 기대 정책을 어긴 응답이나 도구 실행을 발견하지 않았고, 자동 통과를 실제 실패로 정정할 사례도 발견하지 않았다. 기존 채점기의 한계가 해소되었다는 뜻은 아니다. 예를 들어 CU-02의 마지막 답변, CU-03의 질문 내용, CU-04의 본인 확인 유지 여부는 여전히 대화 기록을 읽어 확인해야 한다. CU-02의 후속 답변들이 이미 설명한 3영업일 단계와 주문번호 제안을 덧붙인 것은 관찰되었지만, **1~2영업일 답을 대체하거나 잘못된 기간을 안내한 오류는 아니었다**.

18개 고객 턴에서 모델 호출은 **39회(에이전트 27회, 근거 판정 12회)**였다. [summary.json](../../eval_results/experiments/20261129-customer-cases/summary.json)의 추정 비용은 **$0.01569**다. 원시 호출별 추정 비용 합계는 `$0.015695`(약 `$0.01570`)이며, 차이는 집계기가 에이전트·판정 비용을 각각 소수점 다섯 자리로 반올림한 뒤 합산하기 때문에 생긴다. 실제 청구액을 확인한 수치는 아니다.

**적용 범위:** 새 정책 기반 예시 5건의 이번 15회 관찰 결과다. 전체 dev 45문항을 모델로 다시 평가하지 않았으므로 전체 dev 통과율이나 **85% 게이트 충족 여부는 이번 실행에서 측정하지 않았다**. [기존 게이트](../../eval_results/gate.json)는 그대로이며, 결과를 본 뒤 문항·기대값·채점기·프롬프트를 수정하지 않았다. 실제 고객 질문을 수집한 자료가 아니고 별도의 사용자 검수 결과도 없으므로 실제 고객 분포나 고객 응대 성공률로 일반화하지 않는다.

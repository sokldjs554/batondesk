# 평가

> 모든 주문·고객·정책 데이터는 가상의 예시 쇼핑몰 "바통마켓"의 **예시 데이터**입니다.

## 먼저 읽을 것 — 지금 있는 숫자와 없는 숫자

| 평가 | 모델 호출 | 상태 |
|---|---|---|
| 검색 품질 | 없음 | **측정됨** (아래 3절) |
| 채점기 점검(무행동 기준선) | 없음 | **측정됨** (아래 2.4절) |
| 에이전트 전체 평가 | 실제 Claude 호출 | **아직 실행하지 못함** |
| 근거 일치 판정기 | 실제 Claude 호출 | **아직 실행하지 못함** (규칙 검사 부분만 측정됨, 4절) |
| 해결 여부 판정기 | 실제 Claude 호출 | **아직 실행하지 못함** |
| 프롬프트 버전 비교 | 실제 Claude 호출 | **아직 실행하지 못함** — 프롬프트는 v1 하나뿐이다 |

실제 모델을 부르는 평가는 API 키가 GitHub Actions 시크릿에만 있어서 Actions에서 돌려야 하는데,
이 문서를 쓰는 시점에 저장소로의 push 가 막혀 있어 워크플로를 한 번도 실행하지 못했다.
그래서 **답변 품질·인계 판단·판정기 정확도·지연 시간·비용에 대한 숫자는 이 저장소에 없다.**
평가 자료, 실행기, 채점기, 워크플로는 준비되어 있고, 실행 방법은 6절에 있다. 실행하면 이 표와 아래 절을 실측값으로 바꿔야 한다.

테스트에 쓰는 규칙 엔진과 대역(QueueLLM)은 LLM이 아니다. 그것으로 얻은 통과율은 배선 확인일 뿐 품질 수치가 아니며, 이 문서에 싣지 않았다.

## 1. 무엇을 따로 재는가

전체 점수 하나로는 어디가 틀렸는지 알 수 없어서 네 가지를 따로 잰다.

| 무엇 | 어떻게 | 자료 |
|---|---|---|
| 검색 품질 | 질의마다 정답 청크가 k위 안에 있는지. 모델 호출 없음 | `data/evals/retrieval/` |
| 답변의 근거 일치 | (a) 판정기 자체의 정확도: 라벨된 답변을 판정시켜 어긋난 답을 잡는 비율과 멀쩡한 답을 통과시키는 비율 (b) 파이프라인: 틀린 초안을 주입했을 때 고객에게 나가지 않는 비율 | `data/evals/grounding/`, 에이전트 자료의 `ungrounded_injection` |
| 대화 해결 여부 | 라벨된 대화를 판정시킨 5분류 정확도와, 미해결을 미해결로 맞히는 비율 | `data/evals/resolution/` |
| 상담원 인계 여부 | 인계해야 하는 문항에서 인계했는지(재현율), 인계하면 안 되는 문항에서 하지 않았는지(과잉 인계율) | `data/evals/agent/` |

### 2.2 개발용과 평가용의 분리

- 프롬프트·검색 설정을 고칠 때는 **개발용만** 본다. 평가용은 고친 결과를 확인할 때만 돌린다.
- 평가용 파일은 `data/evals/FROZEN.json` 에 sha256 으로 동결했고, CI와 테스트가 대조한다. 바꾸려면 이 문서의 변경 기록(7절)에 이유를 남겨야 한다.
- 두 자료는 같은 방식으로 같은 시점에 만들었고 분류 비율이 같다. 같은 질문이 양쪽에 있지 않은지 테스트가 확인한다
  (에이전트: 문장 일치, 부품별 자료: 문장 일치 + 문자 3-gram 자카드 0.8 초과).
- 검색 평가용은 한 번 측정했다. 그 뒤로 검색 설정을 바꾸지 않았다.

### 2.3 정답은 누가 만들었나

**모든 문항과 정답 라벨은 AI(Claude)가 작성했다. 사람이 검수하지 않았다.**

- 정답의 출처는 모델의 기억이 아니라 저장소 안의 자료다: 지식 문서(`kb/`)와, 시계를 2026-11-20 10:00 KST로 고정한 예시 주문 시스템의 응답. 판정기 자료의 근거 본문은 지식 문서 청크와 글자 그대로 같은지 검증 스크립트가 확인한다.
- 문항마다 `note` 에 그 정답인 이유를 적었다.
- 그래도 작성자가 한 명(AI)이고 질문도 AI가 썼다. 실제 고객의 질문 분포가 아니며, 라벨에 논쟁의 여지가 있는 문항이 있다:
  - 근거 판정기: `G-T-008`(정책을 적용해 계산한 환불액), `G-D-012`·`G-T-019`(낡았지만 날짜로 만료되지는 않은 FAQ), `G-T-021`(근거 밖 문서에 있는 금액)
  - 해결 판정기: `R-D-013`·`R-T-022`(체념한 말투 → 미해결로 라벨), `R-T-024`(절반만 답함), `R-T-030`(재확인 요청 → 대기로 라벨)
- **사람이 할 일**: 평가용 문항을 직접 읽고 라벨에 동의하는지 확인하는 것. 방법은 `docs/how-this-was-built.md` 의 재현 체크리스트에 있다. 확인하기 전까지는 "사람 검수를 거친 평가"라고 말할 수 없다.

### 2.4 채점 기준 (에이전트)

채점은 전부 규칙이다(`src/batondesk/evals/graders.py`). LLM 판정을 쓰지 않는다.

| 성질 | 통과 조건 | 통과 여부에 반영 |
|---|---|---|
| 행동 | 마지막 응답의 행동(답변/되묻기/인계)이 기대한 범위 안 | ○ |
| 사실 | 꼭 들어가야 할 표현(동의어 묶음 중 하나)이 모두 있고, 있어서는 안 되는 표현이 없음 | ○ |
| 모른다고 말하기 | 문서에 없는 내용: 인계했거나, 확인되지 않는다는 뜻의 표현이 있음 | ○ |
| 도구 | 불러야 할 도구를 불렀고, 실행되면 안 되는 도구가 실행되지 않음 | ○ |
| 주문 상태 | 대화가 끝난 뒤 예시 주문 시스템의 주문 상태가 기대와 같음(바뀌면 안 되는 주문은 그대로) | ○ |
| 주입 차단 | 주입한 틀린 내용이 고객에게 보이는 글에 없음 | ○ |
| 인계 사유 | 인계했다면 사유가 기대한 값 중 하나 | × (따로 보고) |
| 정답 문서 인용 | 답변이 정답 문서의 청크를 인용 | × (따로 보고) |
| 검색 | 첫 검색 / 턴 전체에서 정답 문서를 확보 | × (따로 보고) |

- 문자열 비교는 공백·쉼표·물결표 종류를 무시한다("3,000 원" = "3000원", "1∼3" = "1~3").
- **알려진 한계**: 문자열 채점은 같은 뜻의 다른 표현을 놓친다("삼천 원", "일주일"을 "이레"로). 첫 실행 뒤 실패 문항을 읽어 채점 오류인지 확인해야 하고, 채점 기준을 고치면 7절에 적는다.
- 근거 주입 문항에서 모델이 답변이 아니라 인계를 골라 주입이 일어나지 않으면 그 실행은 통과율 분모에서 빼고 건수를 따로 적는다.

**채점기 점검 — 아무 일도 하지 않는 정책** (모델 호출 없음, `python -m batondesk.evals baselines`)

채점이 느슨하면 아무것도 안 하는 정책이 높은 점수를 받는다. 세 가지 무행동 정책의 통과율:

| 정책 | 개발용 (36문항) | 평가용 (58문항) |
|---|---:|---:|
| 항상 상담원에게 넘김 | 27.8% | 25.9% |
| 항상 "확인되지 않습니다" | 16.7% | 17.2% |
| 항상 주문번호를 되물음 | 5.6% | 3.4% |

(근거 주입 문항 4 / 6개는 주입이 일어나지 않으므로 제외.) "항상 넘김"이 26%쯤 받는 것은 인계가 정답인 문항과 문서에 답이 없는 문항 때문이다.
실제 실행의 통과율은 이 값과 나란히 읽어야 한다. CI는 이 값이 35%를 넘으면 실패한다.
인계해야 하는 문항만 있으면 "항상 넘김"이 만점이 되므로, 인계하면 안 되는 문항을 그 두 배 넘게 두었다.

### 2.5 실행 방식 (에이전트)

- 평가용으로 따로 짠 호출 경로가 없다. 서비스가 쓰는 `SupportService.handle_customer_message` 를 그대로 부른다.
- 문항·반복마다 새 샌드박스(예시 주문 데이터 사본)와 새 대화를 쓴다. 앞 실행이 취소한 주문이 다음 채점에 섞이지 않는다.
- 같은 문항을 여러 번 반복 실행한다(기본 3회). 모델은 온도 설정을 받지 않아 실행마다 결과가 달라질 수 있다.
- 통과율의 구간은 문항 단위 부트스트랩 95% 구간이다(반복은 문항에 묶어 뽑는다. 반복 3회를 표본 3개로 세면 구간이 거짓으로 좁아진다).
- 모델 API의 일시 장애(한도 초과·서버 오류·연결 실패)는 최대 3번 다시 실행하고, 끝내 실패하면 `errors.jsonl` 에 남긴다. 통과율에 0으로 섞지 않는다. 모델의 거절·잘린 출력·형식 오류는 모델의 결과이므로 채점한다.
- 응답의 모델 이름이 요청한 모델과 다르면 그 호출을 실패로 처리한다.
- 문항별 채점, 대화 전문, 턴별 실행 기록(검색 결과, 도구 호출, 판정, 토큰, 지연 시간)을 모두 저장한다.

## 3. 검색 품질 (측정됨)

- 조건: 모델 호출 없음. 지식 문서 23건(72청크). 형태소 BM25 + 문자 n-gram 융합. 이 저장소의 컨테이너(리눅스, 파이썬 3.12)에서 실행.
- 적중 기준: 정답 청크 중 하나가 k위 안. 여러 문서를 함께 봐야 하는 질의는 정답 청크가 전부 k위 안.
- 원자료: `eval_results/retrieval/dev.json`, `test.json` (놓친 질의 목록 포함)

**평가용 40문항**

| 구성 | 1위 적중 | 3위 내 | 5위 내 | MRR@10 |
|---|---:|---:|---:|---:|
| 융합 + 유의어 확장 (서비스 구성) | 47.5% | 70.0% | 77.5% | 0.600 |
| 융합, 유의어 확장 없음 | 45.0% | 67.5% | 77.5% | 0.577 |
| BM25만 | 50.0% | 65.0% | 67.5% | 0.585 |
| 문자 n-gram만 | 45.0% | 62.5% | 72.5% | 0.565 |

질의 종류별 5위 내 적중(서비스 구성, 평가용): 문서 표현 그대로 100% (10) · 바꿔 말하기 66.7% (12) · 구어체 70.0% (10) · 오타·띄어쓰기 75.0% (4) · 여러 문서 75.0% (4)

**읽는 법과 한계**

- 융합은 5위 내 적중에서 단일 랭커보다 5~10%p 높다. 문항이 40개라 한 문항이 2.5%p다. 이 차이를 크다고 말할 수는 없다.
- **유의어 확장은 평가용에서 효과가 확인되지 않았다.** 개발용에서는 5위 내 적중이 75% → 90%로 올랐지만(개발용의 실패 질의를 보고 사전을 만들었으니 당연하다) 평가용은 77.5% 그대로다. 개발용에 맞춘 사전이 새 질의로 일반화되지 않았다는 뜻이다.
- 문서와 다른 말로 묻는 질의 넷 중 하나쯤은 첫 검색에서 정답 문서를 5위 안에 올리지 못한다. 예: "산 지 열 달 된 청소기가 멈췄는데 공짜로 고쳐주나요"(보증 문서), "요즘 택배 좀 늦는다던데 맞아요?"(연말 배송 공지).
- 에이전트는 검색 도구로 질의를 바꿔 다시 찾을 수 있다. 그것이 이 빈틈을 얼마나 메우는지는 에이전트 평가의 "턴 안에 정답 문서 확보" 지표로 재야 하는데, 아직 실행하지 못했다.
- 질의는 AI가 썼다. 실제 고객 질의로 재면 수치가 달라질 수 있다.

## 4. 근거 일치 판정기 — 규칙 검사 부분만 (모델 호출 없음)

판정기는 규칙 검사와 LLM 판정 두 겹이다. LLM 판정은 아직 실행하지 못했고, 규칙 검사만 단독으로 잰 결과다
(`python -m batondesk.evals grounding --split test --rules-only`).

"잡는다"는 근거에서 찾지 못한 금액·날짜·비율·주문번호가 하나라도 있다는 뜻이다.

| 자료 | 어긋난 답을 잡은 비율(재현율) | 멀쩡한 답을 통과시킨 비율(특이도) |
|---|---:|---:|
| 평가용 40문항 (어긋남 20 / 맞음 20) — 첫 측정 | 30.0% (6/20) | 85.0% (17/20) |
| 평가용 40문항 — 규칙 수정 뒤 | 30.0% (6/20) | 95.0% (19/20) |
| 개발용 24문항 (12 / 12) | 33.3% (4/12) | 91.7% (11/12) |

- 첫 측정에서 멀쩡한 답 3건을 잘못 걸렀다. 두 건은 규칙의 빈틈이었다: 도구 결과의 `"return_fee": 0` 을 "0원"과 잇지 못했고, `05:12` 를 "오전 5시 12분"과 잇지 못했다. 고쳤다(`checks/facts.py`). **이 수정은 평가용 결과를 보고 한 것**이라, 수정 뒤의 평가용 95.0%는 깨끗한 수치가 아니다. 개발용 수치는 수정 전후가 같다.
- 남은 오탐 1건(`G-T-008`)은 근거의 값으로 계산한 금액이다. 규칙으로는 구분할 수 없어 LLM 판정에 맡기는 부분이다.
- 종류별(평가용): 금액 바꾸기 3/3은 잡지만, 기간 바꾸기 0/2 · 가능/불가 뒤집기 0/3 · 한 구절만 틀린 답 0/3 · 주문 사실 오류 0/2는 못 잡는다. 기간은 계산으로 나온 기간과 구분할 수 없어 일부러 막지 않는다(`docs/design-decisions.md` D3).

규칙 검사는 숫자가 바뀐 답만 잡을 수 있다. 지어낸 정책, 근거 없는 약속, 가능/불가를 뒤집은 답은 규칙으로 잡히지 않는다 — LLM 판정이 필요한 이유이고, 그 정확도는 아직 모른다.

## 5. 아직 측정하지 못한 것

실제 모델로 워크플로를 실행하면 다음을 채운다. 지금은 빈칸이다.

- 에이전트 통과율(전체·분류별), 인계 재현율과 과잉 인계율, 주문 상태 일치, 주입 차단
- 반복마다 결과가 갈리는 문항, 모든 반복에서 실패하는 문항과 그 원인
- 근거 일치 판정기: 어긋난 답을 잡는 비율, 멀쩡한 답을 통과시키는 비율, 종류별 정확도, 반복 간 일치율, 놓친 문항 목록
- 해결 여부 판정기: 5분류 정확도, 미해결을 해결이라고 한 문항 목록
- 프롬프트 v1 → v2 비교(같은 문항, 짝지은 차이와 구간, 좋아진 문항과 나빠진 문항)
- 지연 시간(턴·단계별 p50/p95)과 토큰·추정 비용 — 제시할 때 모델, 호출 횟수, 실행 환경(GitHub Actions 러너), 문항 수와 반복 횟수를 함께 적는다

프롬프트 개선 절차(계획): 개발용을 v1로 3회 반복 실행 → 실패 문항을 읽고 원인을 분류 → v2 작성(무엇을 왜 바꿨는지 `changes` 에 기록) → 개발용으로 v1과 비교 → 평가용으로 두 버전을 각각 3회 실행해 짝지은 차이를 보고 → 채택한 버전을 `prompts/manifest.yaml` 의 active 로 올리고 게이트 기준을 정한다.

## 6. 실행 방법

모델을 부르지 않는 것(로컬에서 바로 실행):

```bash
python -m batondesk.evals retrieval --split test
python -m batondesk.evals baselines --split test
python -m batondesk.evals grounding --split test --rules-only
python -m batondesk.evals check-frozen
python scripts/validate_eval_data.py
```

실제 모델을 부르는 것(GitHub Actions의 `eval-live` 워크플로를 수동 실행. 저장소 시크릿 `ANTHROPIC_API_KEY` 필요):

| 무엇을 보려는가 | 입력 |
|---|---|
| 모델 호출이 되는지만 | suite=`smoke-only` |
| 개발용 기준선 | suite=`agent`, split=`dev`, reps=`3`, label=`v1-dev` |
| 판정기 정확도 | suite=`judges`, split=`both`, reps=`3`, label=`judges-v1` |
| 프롬프트 버전 비교 | 같은 split·reps 로 agent_prompt 만 바꿔 두 번 실행한 뒤 `python -m batondesk.evals compare <A 폴더> <B 폴더>` |
| 모델 비교 | 같은 조건에서 agent_model 만 바꿔 실행 |
| 데모용 상담 기록 | suite=`record-demo` |

결과는 실행의 Summary 탭, 아티팩트, `eval-runs` 브랜치의 `runs/<실행 id>/` 에 남는다(`manifest.json`, `summary.json`, `results.jsonl`, `errors.jsonl`, `trajectories.jsonl.gz`).
키가 있는 환경이면 같은 명령을 로컬에서도 돌릴 수 있다: `ANTHROPIC_API_KEY=… python -m batondesk.evals agent --split dev --reps 3 --label v1-dev`.

# 평가

> 모든 주문·고객·정책 데이터는 가상의 예시 쇼핑몰 "바통마켓"의 **예시 데이터**입니다.
> 이 문서의 수치는 모두 **자동 평가**입니다. 사람 검수와 실제 사용자 평가는 받지 않았습니다(2.3절, 8절).

## 먼저 읽을 것 — 결론

모델은 `claude-haiku-5-5`(에이전트와 판정기 모두, effort low), 실행 환경은 GitHub Actions(ubuntu-24.04) 러너, 날짜는 2026-11-26 이다.
**평가용(test)은 프롬프트와 파이프라인을 고치는 동안 한 번도 돌리지 않았고**, 마지막에 같은 커밋(`2cec3ec`)에서 기준선(v1 프롬프트)과 최종 구성(v4 프롬프트)을 각각 3회 반복 실행했다.

| 무엇 | 자료 | 기준선 (agent-v1 + grounding-v1) | 최종 (agent-v4 + grounding-v4) |
|---|---|---:|---:|
| 에이전트 통과율 — 동결된 채점 그대로 | 평가용 64문항 × 3회 | 89.1% [81.8, 95.3] | 89.6% [82.8, 95.3] |
| 에이전트 통과율 — 채점 오류 4문항을 고친 뒤 재채점 (6.3절) | 같은 실행 | 92.2% [85.9, 97.4] | 92.7% [87.0, 97.4] |
| 같은 문항끼리의 차이 (최종 − 기준선) | 64문항 | — | **+0.5%p [−3.6, +5.2]** |
| 인계해야 할 때 인계함 / 하면 안 될 때 인계함 | 평가용 | 97.0% (32/33) / 0.9% (1/117) | 97.0% (32/33) / 3.4% (4/117) |
| 주입한 틀린 초안이 고객에게 나가지 않음 (재채점) | 평가용 6문항 × 3회 | 18/18 | 18/18 |
| 대화가 끝난 뒤 주문 상태가 기대와 같음 | 평가용 192회 | 100% | 100% |
| 턴 지연 p50 / p95 | 평가용 225턴 | 6.6초 / 15.0초 | 5.5초 / 10.0초 |
| 추정 비용 (192회 대화 실행 전체) | 평가용 | $0.267 | $0.227 |
| 근거 판정기: 어긋난 답을 잡음 / 멀쩡한 답을 통과 | 평가용 54문항 × 3회 | 78/78 / 80/84 | 78/78 / 77/84 |
| 해결 판정기: 5분류 정확도 / 미해결을 해결이라고 함 | 평가용 36문항 × 3회 | 97.2% [91.7, 100] / 0건 | (같은 프롬프트) |
| 검색: 정답 청크가 5위 안 | 평가용 40문항 | 77.5% | (같은 검색) |

대괄호는 문항 단위 부트스트랩 95% 구간이다.

**이 표가 말하는 것**

1. **프롬프트를 v1 에서 v4 로 고친 것은 평가용 통과율을 올리지 못했다.** 차이의 구간이 0을 가운데 두고 있다. 개발용에서는 94.2% → 97.5% 로 보였지만(6.1절) 평가용에서 재현되지 않았다. 개발용 40문항의 실패를 보고 고친 문장이 새 문항으로 일반화되지 않았다는 뜻이다.
2. v4 로 바뀐 것은 속도와 비용이다: 턴 지연 p95 가 15.0초에서 10.0초로, 추정 비용이 15% 줄었다. 판정기 출력이 짧아지고(4.2절) 답변이 짧아진 결과다. 대신 필요 없는 인계가 1건에서 4건으로 늘었다.
3. 서비스의 기본 프롬프트를 v4 로 올렸다(`prompts/manifest.yaml`). **이유는 "품질이 좋아져서"가 아니라 "통과율이 같은 수준에서 지연과 비용이 낮아서"다.** 늘어난 과잉 인계는 알려진 회귀로 남겼다(6.4절).
4. 통과율을 실제로 움직인 것은 프롬프트가 아니라 파이프라인과 채점기였다: 판정기에 상담 정보를 주고, 실패한 도구 호출을 근거로 남기고, 공지의 나머지 절을 함께 검색하게 한 뒤 **같은 v1 프롬프트**의 개발용 통과율이 89~91% 에서 94.2% 로 올랐다(6.1절). 다만 이 수정들은 개발용을 보고 한 것이고, 평가용에서 수정 전후를 따로 재지 않았다.
5. 평가용에서 고객에게 **틀리거나 빠진 정책 답이 나간** 문항이 두 개 있고(64문항 중 2문항, 두 구성 모두 3회 다 실패), 둘 다 원인은 검색이다(6.4절). 근거 검사는 이것을 잡지 못한다 — 답변이 "검색된 문서"와는 맞기 때문이다.
6. 평가용을 읽다가 **채점 규칙이 맞는 답을 틀렸다고 한 문항 4개**를 찾았다. 고치기 전 수치와 고친 뒤 수치를 둘 다 적었다. 두 구성에 똑같이 적용되므로 비교 결론은 바뀌지 않는다.

**이 표가 말하지 않는 것**: 문항과 정답 라벨은 전부 AI가 썼고 사람이 검수하지 않았다. 실제 고객 질문이 아니다. 문항 수가 적어(64문항) 3~5%p 차이는 구분하지 못한다. 한 모델, 한 날짜, 한 환경에서 잰 값이다.

테스트에 쓰는 규칙 엔진과 대역(QueueLLM)은 LLM이 아니다. 그것으로 얻은 통과율은 배선 확인일 뿐 품질 수치가 아니며, 이 문서에 싣지 않았다.

### 2.2 개발용과 평가용의 분리

- 프롬프트·검색 설정을 고칠 때는 **개발용만** 본다. 평가용은 고친 결과를 확인할 때만 돌린다.
- 평가용 파일은 `data/evals/FROZEN.json` 에 sha256 으로 동결했고, CI와 테스트가 대조한다. 바꾸려면 이 문서의 변경 기록(7절)에 이유를 남겨야 한다.
- 두 자료는 같은 방식으로 같은 시점에 만들었고 분류 비율이 같다. 같은 질문이 양쪽에 있지 않은지 테스트가 확인한다
  (에이전트: 문장 일치, 부품별 자료: 문장 일치 + 문자 3-gram 자카드 0.8 초과).
- 검색 평가용은 한 번 측정했다. 그 뒤로 순위를 매기는 설정은 바꾸지 않았다(공지의 나머지 절을 함께 주는 수정은 순위를 바꾸지 않는다).
- 에이전트·판정기 평가용은 **모든 수정이 끝난 뒤** 한 번 실행했다. 기준선과 최종 구성을 같은 커밋에서 돌렸다. 평가용 결과를 본 뒤에는 프롬프트와 파이프라인을 바꾸지 않았다. 바꾼 것은 채점 규칙 오류 4문항뿐이고, 그 전후 수치를 모두 적었다(6.3절).

### 2.3 정답은 누가 만들었나

**모든 문항과 정답 라벨은 AI(Claude)가 작성했다. 사람이 검수하지 않았다.**

- 정답의 출처는 모델의 기억이 아니라 저장소 안의 자료다: 지식 문서(`kb/`)와, 시계를 2026-11-20 10:00 KST로 고정한 예시 주문 시스템의 응답. 판정기 자료의 근거 본문은 지식 문서 청크와 글자 그대로 같은지 검증 스크립트가 확인한다.
- 문항마다 `note` 에 그 정답인 이유를 적었다.
- 그래도 작성자가 한 명(AI)이고 질문도 AI가 썼다. 실제 고객의 질문 분포가 아니며, 라벨에 논쟁의 여지가 있는 문항이 있다:
  - 근거 판정기: `G-T-008`(정책을 적용해 계산한 환불액), `G-D-012`·`G-T-019`(낡았지만 날짜로 만료되지는 않은 FAQ), `G-T-021`(근거 밖 문서에 있는 금액)
  - 해결 판정기: `R-D-013`·`R-T-022`(체념한 말투 → 미해결로 라벨), `R-T-024`(절반만 답함), `R-T-030`(재확인 요청 → 대기로 라벨)
- **사람이 할 일**: 평가용 문항을 직접 읽고 라벨에 동의하는지 확인하는 것. 방법은 `docs/how-this-was-built.md` 의 재현 체크리스트에 있다. 확인하기 전까지는 "사람 검수를 거친 평가"라고 말할 수 없다.

### 2.4 채점 기준 (에이전트)

채점은 전부 규칙이다(`src/batondesk/evals/graders.py`). LLM 판정을 쓰지 않는다.

| 성질 | 통과 조건 | 통과 여부에 반영 |
|---|---|---|
| 행동 | 마지막 응답의 행동(답변/되묻기/인계)이 기대한 범위 안 | ○ |
| 사실 | 꼭 들어가야 할 표현(동의어 묶음 중 하나)이 모두 있고, 있어서는 안 되는 표현이 없음 | ○ |
| 모른다고 말하기 | 문서에 없는 내용: 인계했거나, 확인되지 않는다는 뜻의 표현이 있음 | ○ |
| 도구 | 불러야 할 도구를 불렀고, 실행되면 안 되는 도구가 실행되지 않음 | ○ |
| 주문 상태 | 대화가 끝난 뒤 예시 주문 시스템의 주문 상태가 기대와 같음(바뀌면 안 되는 주문은 그대로) | ○ |
| 주입 차단 | 주입한 틀린 내용이 고객에게 보이는 글에 없음 | ○ |
| 인계 사유 | 인계했다면 사유가 기대한 값 중 하나 | × (따로 보고) |
| 정답 문서 인용 | 답변이 정답 문서의 청크를 인용 | × (따로 보고) |
| 검색 | 첫 검색 / 턴 전체에서 정답 문서를 확보 | × (따로 보고) |

- 문자열 비교는 공백·쉼표·물결표 종류를 무시한다("3,000 원" = "3000원", "1∼3" = "1~3").
- **알려진 한계, 그리고 실제로 일어난 일**: 문자열 채점은 같은 뜻의 다른 표현을 놓치고("끝났습니다"를 "지났습니다"로 인정하지 못함), 금지어가 넓으면 맞는 답을 틀렸다고 한다("무료배송 조건을 채워도 추가 배송비는 부과됩니다"에서 "무료"). 실제 실행 뒤 실패를 전부 읽어 개발용에서 3종류, 평가용에서 4문항의 채점 오류를 찾아 고쳤다. 고친 내용은 7절에, 고치기 전후의 수치는 6절에 있다. 예전 실행을 지금 기준으로 다시 채점하는 명령이 있다: `python -m batondesk.evals regrade <실행 폴더>`.
- 근거 주입 문항에서 모델이 답변이 아니라 인계를 골라 주입이 일어나지 않으면 그 실행은 통과율 분모에서 빼고 건수를 따로 적는다.

**채점기 점검 — 아무 일도 하지 않는 정책** (모델 호출 없음, `python -m batondesk.evals baselines`)

채점이 느슨하면 아무것도 안 하는 정책이 높은 점수를 받는다. 세 가지 무행동 정책의 통과율:

| 정책 | 개발용 (36문항) | 평가용 (58문항) |
|---|---:|---:|
| 항상 상담원에게 넘김 | 22.2% | 25.9% |
| 항상 "확인되지 않습니다" | 13.9% | 13.8% |
| 항상 주문번호를 되물음 | 5.6% | 1.7% |

(근거 주입 문항 4 / 6개는 주입이 일어나지 않으므로 제외.) "항상 넘김"이 26%쯤 받는 것은 인계가 정답인 문항과 문서에 답이 없는 문항 때문이다.
실제 실행의 통과율은 이 값과 나란히 읽어야 한다. CI는 이 값이 35%를 넘으면 실패한다.
인계해야 하는 문항만 있으면 "항상 넘김"이 만점이 되므로, 인계하면 안 되는 문항을 그 두 배 넘게 두었다.

### 2.5 실행 방식 (에이전트)

- 평가용으로 따로 짠 호출 경로가 없다. 서비스가 쓰는 `SupportService.handle_customer_message` 를 그대로 부른다.
- 문항·반복마다 새 샌드박스(예시 주문 데이터 사본)와 새 대화를 쓴다. 앞 실행이 취소한 주문이 다음 채점에 섞이지 않는다.
- 같은 문항을 여러 번 반복 실행한다(기본 3회). 모델은 온도 설정을 받지 않아 실행마다 결과가 달라질 수 있다.
- 통과율의 구간은 문항 단위 부트스트랩 95% 구간이다(반복은 문항에 묶어 뽑는다. 반복 3회를 표본 3개로 세면 구간이 거짓으로 좁아진다).
- 모델 API의 일시 장애(한도 초과·서버 오류·연결 실패)는 최대 3번 다시 실행하고, 끝내 실패하면 `errors.jsonl` 에 남긴다. 통과율에 0으로 섞지 않는다. 모델의 거절·잘린 출력·형식 오류는 모델의 결과이므로 채점한다.
- 응답의 모델 이름이 요청한 모델과 다르면 그 호출을 실패로 처리한다.
- 문항별 채점, 대화 전문, 턴별 실행 기록(검색 결과, 도구 호출, 판정, 토큰, 지연 시간)을 모두 저장한다.

## 3. 검색 품질 (측정됨)

- 조건: 모델 호출 없음. 지식 문서 23건(72청크). 형태소 BM25 + 문자 n-gram 융합. 이 저장소의 컨테이너(리눅스, 파이썬 3.12)에서 실행.
- 적중 기준: 정답 청크 중 하나가 k위 안. 여러 문서를 함께 봐야 하는 질의는 정답 청크가 전부 k위 안.
- 원자료: `eval_results/retrieval/dev.json`, `test.json` (놓친 질의 목록 포함)

**평가용 40문항**

| 구성 | 1위 적중 | 3위 내 | 5위 내 | MRR@10 |
|---|---:|---:|---:|---:|
| 융합 + 유의어 확장 (서비스 구성) | 47.5% | 70.0% | 77.5% | 0.600 |
| 융합, 유의어 확장 없음 | 45.0% | 67.5% | 77.5% | 0.577 |
| BM25만 | 50.0% | 65.0% | 67.5% | 0.585 |
| 문자 n-gram만 | 45.0% | 62.5% | 72.5% | 0.565 |

질의 종류별 5위 내 적중(서비스 구성, 평가용): 문서 표현 그대로 100% (10) · 바꿔 말하기 66.7% (12) · 구어체 70.0% (10) · 오타·띄어쓰기 75.0% (4) · 여러 문서 75.0% (4)

**읽는 법과 한계**

- 융합은 5위 내 적중에서 단일 랭커보다 5~10%p 높다. 문항이 40개라 한 문항이 2.5%p다. 이 차이를 크다고 말할 수는 없다.
- **유의어 확장은 평가용에서 효과가 확인되지 않았다.** 개발용에서는 5위 내 적중이 75% → 90%로 올랐지만(개발용의 실패 질의를 보고 사전을 만들었으니 당연하다) 평가용은 77.5% 그대로다. 개발용에 맞춘 사전이 새 질의로 일반화되지 않았다는 뜻이다.
- 문서와 다른 말로 묻는 질의 넷 중 하나쯤은 첫 검색에서 정답 문서를 5위 안에 올리지 못한다. 예: "산 지 열 달 된 청소기가 멈췄는데 공짜로 고쳐주나요"(보증 문서), "요즘 택배 좀 늦는다던데 맞아요?"(연말 배송 공지).
- 에이전트는 검색 도구로 질의를 바꿔 다시 찾을 수 있다. **그런데 그것이 이 빈틈을 메우지 못했다.** 평가용 에이전트 실행에서 "첫 검색에 정답 문서 확보"와 "턴 전체에서 확보"가 둘 다 96.0%(72/75)로 같았다. 첫 검색이 그럴듯한(하지만 낡은) 문서를 가져오면 모델은 다시 찾지 않는다(6.4절 `A-T-CF-01`).
- 문서 단위로는 맞게 찾았어도 **필요한 절(청크)이 빠지는** 경우가 있다. 위 지표는 문서 단위라 이것을 놓친다(6.4절 `A-T-KB-09`).
- 질의는 AI가 썼다. 실제 고객 질의로 재면 수치가 달라질 수 있다.

## 4. 근거 일치 판정기

판정기는 두 겹이다. 규칙 검사(금액·날짜·비율·주문번호가 근거에 있는지)와 LLM 판정(주장 단위로 근거와 맞는지).
LLM 판정을 쓸 수 있으면 판정은 LLM 것이고, 호출이 실패하면 규칙만으로 막는 쪽으로 떨어진다.

### 4.1 규칙 검사만 (모델 호출 없음)

`python -m batondesk.evals grounding --split test --rules-only`. "잡는다"는 근거에서 찾지 못한 금액·날짜·비율·주문번호가 하나라도 있다는 뜻이다.

| 자료 | 어긋난 답을 잡음 | 멀쩡한 답을 통과 |
|---|---:|---:|
| 평가용 54문항 (어긋남 26 / 맞음 28) | 30.8% (8/26) | 92.9% (26/28) |
| 그중 첫 작성분 40문항 — 첫 측정 | 30.0% (6/20) | 85.0% (17/20) |
| 그중 첫 작성분 40문항 — 규칙 수정 뒤 | 30.0% (6/20) | 95.0% (19/20) |
| 개발용 33문항 (16 / 17) | 37.5% (6/16) | 88.2% (15/17) |

- 첫 측정에서 멀쩡한 답 3건을 잘못 걸렀다. 두 건은 규칙의 빈틈이었다(도구 결과의 `"return_fee": 0` 을 "0원"과, `05:12` 를 "오전 5시 12분"과 잇지 못함). 고쳤다. **이 수정은 평가용 결과를 보고 한 것**이라 수정 뒤의 95.0%는 깨끗한 수치가 아니다.
- 규칙은 숫자가 바뀐 답만 잡는다. 지어낸 정책, 근거 없는 약속, 가능/불가를 뒤집은 답, 하지 않은 처리를 했다고 하는 답은 잡지 못한다. 계산으로 나온 값은 틀렸다고 잘못 잡는다. LLM 판정이 필요한 이유다.

### 4.2 LLM 판정 — 프롬프트 네 버전

라벨된 답변(근거, 대화, 답변, 맞음/어긋남)을 판정시켜 맞히는지 본다. 문항마다 3회 반복.

**개발용** (프롬프트를 고칠 때 본 자료)

| 판정 프롬프트 | 문항×반복 | 어긋난 답을 잡음 | 멀쩡한 답을 통과 | 틀린 구절을 짚음 | 반복 3회가 같은 판정 | 출력 토큰 | 호출 지연 p50 | 실행 |
|---|---:|---:|---:|---:|---:|---:|---:|---|
| grounding-v1 (첫 자료 24건, 상담 정보 없음) | 24×3 | 36/36 | 36/36 | 33% | 100% | 25,490 | 1.94초 | `…094034-grounding-dev-judges-v1-dev` |
| grounding-v1 | 33×3 | 48/48 | 47/51 | 48% | 97% | 46,518 | 1.85초 | `…122157-grounding-dev-g1-dev33` |
| grounding-v2 | 33×3 | 48/48 | 45/51 | 94% | 91% | 28,451 | 1.26초 | `…122156-grounding-dev-g2-dev33` |
| grounding-v3 | 33×3 | 48/48 | 51/51 | 90% | 100% | 27,938 | 1.43초 | `…123244-grounding-dev-g3-dev33` |
| grounding-v4 | 33×3 | 48/48 | 51/51 | 94% | 100% | 27,824 | 1.34초 | `…123947-grounding-dev-g4-dev33` |

**평가용** (고치는 동안 보지 않은 자료, 54문항 × 3회 = 162회)

| 판정 프롬프트 | 정확도 [95% 구간] | 어긋난 답을 잡음 | 멀쩡한 답을 통과 | 첫 작성분 40문항 | 추가 14문항 | 틀린 구절을 짚음 | 출력 토큰 | 호출 지연 p50 / p95 | 추정 비용 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| grounding-v1 | 97.5% [93.2, 100] | 78/78 | 95.2% (80/84) | 120/120 | 38/42 | 49% | 71,826 | 2.03초 / 2.88초 | $0.047 |
| grounding-v4 | 95.7% [90.1, 100] | 78/78 | 91.7% (77/84) | 113/120 | 42/42 | 97% | 44,295 | 1.23초 / 2.07초 | $0.036 |

읽은 것:

1. **처음 만든 자료는 판정기를 가르지 못했다.** 첫 실행에서 v1 이 72/72 를 맞혔는데, 같은 판정기가 실제 에이전트 초안에서는 상담 진행 안내("확인해 드리겠습니다"), 고객 이름, 현재 시각을 근거 없음으로 막고 있었다(4.3절). 자료에 그 유형이 없었다. 실제로 막힌 초안과 그 변형으로 자료를 늘렸다(7절).
2. **v2 는 v1 보다 낫지 않았다.** 멀쩡한 답 통과가 47/51 → 45/51. 새로 넣은 "확정되지 않은 금액" 기준을 판정기가 넓게 읽어, v1 이 통과시키던 문항(`G-D-005`)을 막았다. 얻은 것은 출력 토큰 39% 감소와 틀린 구절 짚기(48% → 94%)였다. v3 에서 그 기준을 좁히고 상담 AI의 운영 규칙을 적었고, v4 에서 도구로 할 수 있는 일을 적었다. 버전마다 무엇을 왜 바꿨는지는 `prompts/grounding/v*.yaml` 의 `changes` 에 실행 이름·문항 ID와 함께 있다.
3. **평가용에서 v4 는 v1 보다 정확하지 않다.** 겨냥한 유형(상담 진행 안내)은 고쳐졌다 — 추가 14문항에서 38/42 → 42/42. 그런데 v1 이 다 맞히던 첫 작성분에서 7건을 잘못 막았다(120/120 → 113/120): `G-T-009`(계산한 배송비, 2/3), `G-T-013`(날짜 계산, 2/3), `G-T-020`(만료된 공지를 바꿔 말함, 3/3). 한 종류의 오탐을 줄이고 다른 종류의 오탐을 얻은 것이다. 정확도의 차이(97.5% vs 95.7%)는 구간이 겹친다.
4. v4 가 잘못 막은 문항의 이유 문장을 보면 "계산은 맞습니다. 다만 …"이라고 쓰고도 라벨은 `contradicted` 다. 출력 형식이 `label` 을 `reason` 보다 먼저 쓰게 되어 있고(`checks/grounding.py` 의 스키마), v2 부터 맞는 주장에는 이유를 쓰지 않게 했다. 따져 보기 전에 라벨을 정하게 만든 것이 원인일 수 있다. **확인하지 않은 가설이다.** 다음에 해 볼 것: 이유를 라벨 앞에 두는 스키마로 같은 자료를 다시 재기.
5. 어긋난 답은 두 버전 모두 하나도 놓치지 않았다(78/78). 다만 이 자료의 틀린 답은 AI가 "숫자를 바꾼다, 약속을 덧붙인다" 식으로 만든 것이다. 실제 모델이 내는 미묘한 오류에 대한 재현율은 이 숫자보다 낮을 것이다.
6. 종류별(평가용, v1 / v4): 상담 진행 안내 8/12 / 12/12 · 계산한 값 12/12 / 10/12 · 만료 문서를 올바르게 다룬 답 9/9 / 6/9 · 여러 근거를 합친 답 9/9 / 7/9 · 나머지 14종은 둘 다 전부 맞음.

### 4.3 파이프라인 안에서

**(a) 주입한 틀린 초안**: 에이전트 평가에는 모델의 첫 초안을 정해 둔 틀린 답으로 바꿔치기하는 문항이 있다(개발용 4, 평가용 6). 개발용은 모든 실행에서 12/12(3회 반복) 차단되었다. 평가용은 채점 당시 14/18(v1), 15/18(v4)로 나왔는데, 7건을 전부 읽어 보니 판정기는 주입한 초안을 매번 막았고 최종 답변도 맞았다. 채점 규칙의 금지어가 넓어 맞는 답에 걸린 것이었다(6.3절). 고친 채점으로는 둘 다 18/18 이다.

**(b) 첫 개발용 실행에서 막힌 초안 40건을 전부 읽음** (agent-v1 + grounding-v1, 120회 실행 중 32턴에서 초안 40건이 막힘)

| 분류 (AI가 읽고 나눔, 사람 검수 아님) | 건수 | 예 |
|---|---:|---|
| 맞게 막음 | 17 | 주입한 틀린 답 12, 시스템이 확정하지 않은 회수비를 확정처럼 말한 답 4(`A-D-CF-03`), 근거에 없는 일반론 1 |
| 잘못 막음 | 19 | 상담 진행 안내("확인해 드리겠습니다", "상담원에게 연결해 드리겠습니다") 11, 현재 시각으로 한 판단 3, 고객 이름 호칭·형식 예시로 든 주문번호 4, 근거에서 바로 나오는 추론 1 |
| 판단이 갈림 | 4 | "…로 보입니다" 같은 추정 표현 등 |

막힌 초안은 한 번 다시 쓰게 하고, 그래도 막히면 시스템이 상담원에게 넘긴다(고객에게는 "확인이 더 필요해 상담원에게 연결합니다"가 나간다). 첫 실행에서 그렇게 끝난 8건 중 6건이 잘못 막은 데서 나왔다. 판정기가 엄격한 쪽으로 틀리면 고객에게 틀린 답이 나가지는 않지만, 필요 없는 인계와 지연이 생긴다.
여기서 나온 수정: 판정기 입력에 상담 정보(지금 시각, 고객 이름) 추가(코드), 도구 설명의 주문번호 예시를 실제 주문과 겹치지 않게 변경(코드), 판정 프롬프트 v2~v4.

**(c) 평가용에서**: 주입이 아닌 초안을 막은 턴은 225턴 중 v1 구성 35턴, v4 구성 27턴이다. 재작성 뒤에도 막혀 시스템 인계로 끝난 것은 둘 다 3건이다. 시스템 인계로 끝난 실행 중 통과하지 못한 것을 읽으면 판정기의 오탐이다: 영업일 날짜 계산을 틀렸다고 함(`A-T-CF-05`, 실제로는 맞는 계산), "울릉도는 그 밖의 도서산간에 해당한다"를 근거 없음으로 봄(`A-T-KB-03`). 막힌 35 / 27턴 전체를 맞게 막음·잘못 막음으로 나눠 읽지는 않았다.

1. **①을 읽었다.** 실패 12건과 막힌 초안 40건(4.3절). 판정기가 상담 정보를 몰라 생긴 오탐을 코드에서 고치고(②), 프롬프트 v2 를 썼다(③④).

3. **프롬프트 밖을 고쳤다(⑤).** 공지의 한 절이 검색되면 같은 공지의 나머지 절도 근거로 준다. 실패한 도구 호출(형식 오류, 시스템 오류)도 근거 묶음에 남긴다 — 에이전트는 그 오류 문구를 보고 답하는데 판정기는 못 보고 있었다. 채점기의 "모른다고 말하기" 표현 목록이 "확인하지 못했습니다"를 놓치던 것을 고쳤다. **프롬프트는 v1 그대로인데** 통과율이 94.2% 가 되었다.
4. **v3, v4.** ⑦에서 97.5%. v3 가 넣은 "예외를 부탁하면 넘긴다"가 절차 생략 요구에도 적용되어 `A-D-OT-06` 이 1/3 로 내려가는 회귀가 생겼고, v4 에서 범위를 좁혔다(⑧).
5. 같은 코드에서의 짝지은 차이: ⑤ → ⑦ +3.3%p [−2.5, +10.0], ⑤ → ⑧ +3.3%p [−3.3, +10.8]. **개발용에서도 구간이 0을 포함한다.** 40문항으로는 이 크기의 차이를 확정할 수 없다. 그리고 ⑦⑧의 프롬프트는 이 40문항의 실패를 보고 쓴 것이라 개발용 수치는 낙관적이다. 그래서 평가용이 필요하다.

### 6.6 지연 시간과 비용

조건을 함께 적는다. 모델 `claude-haiku-5-5`(에이전트·판정 모두), effort low, 적응형 사고 사용, 시스템 프롬프트 캐시 사용. GitHub Actions ubuntu-24.04 러너에서 동시 실행 4. 예시 주문 시스템은 같은 프로세스 안에서 호출(네트워크 지연 없음). 평가용 192회 실행 = 225턴.

| | 기준선 (v1 + v1) | 최종 (v4 + v4) |
|---|---:|---:|
| 턴 지연 p50 / p95 / 최대 | 6.6초 / 15.0초 / 30.1초 | 5.5초 / 10.0초 / 13.8초 |
| 단계별 p50: 에이전트 모델 / 판정 모델 / 검색 | 4.7초 / 2.7초 / 1ms | 3.8초 / 1.5초 / 1ms |
| 턴당 모델 호출 (에이전트+판정) | 2.77회 | 2.82회 |
| 모델 호출 수: 에이전트 / 판정 | 431 / 192 | 415 / 220 |
| 출력 토큰: 에이전트 / 판정 | 187,692 / 142,147 | 160,921 / 68,860 |
| 추정 비용: 전체 / 턴당 | $0.267 / $0.0012 | $0.227 / $0.0010 |

- 비용은 청구서가 아니라 **응답의 토큰 수 × 코드에 적어 둔 단가**(`llm/pricing.py`, 2026-11-03 에 옮겨 적은 공개 단가: 입력 $0.10, 출력 $0.50, 캐시 읽기 $0.01 / 100만 토큰)로 계산한 추정치다.
- **턴 하나에 5~6초가 걸린다.** 채팅 상담으로는 느리다. 에이전트 모델 호출(도구를 부르면 2회 이상)과 근거 판정 호출이 차례로 일어나기 때문이다. 화면은 진행 단계("문서를 찾는 중", "근거를 확인하는 중")를 스트림으로 보여 주지만 답변 글자 자체를 흘려보내지는 않는다 — 근거 검사를 통과하기 전의 글을 고객에게 보여 주지 않기 위해서다(`docs/design-decisions.md`).
- 이 수치는 러너 한 대에서 동시 4건으로 돌린 값이다. 동시 접속이 많을 때의 지연, 다른 모델의 지연은 재지 않았다.

### 6.7 회귀 게이트 — 프롬프트·에이전트가 바뀔 때 자동으로 도는 평가

## 8. 사람이 하지 않은 것, 다음에 할 것

- **사람 검수 없음.** 문항, 정답 라벨, 채점 규칙, 실패의 분류(맞게 막음/잘못 막음, 채점 오류/모델 오류)를 모두 AI가 했다. 저장소 주인이 평가용 문항을 직접 읽고 라벨에 동의하는지, 6.3절의 "채점 오류"라는 판단에 동의하는지 확인하기 전에는 "사람이 검수한 평가"라고 말할 수 없다. 확인 방법은 `docs/how-this-was-built.md` 의 체크리스트에 있다.
- **실제 사용자 평가 없음.** 고객 만족, 실제 해결률, 실제 상담원의 인계 품질 평가는 없다. 이 문서의 "해결"은 판정기의 라벨이다.
- 평가용은 이제 한 번 본 자료다. 6.4절의 수정을 하고 그 효과를 말하려면 새 문항이 필요하다.
- 통과한 실행은 읽지 않았다. 틀린 답이 통과로 채점된 경우는 모른다.
- 한 모델(`claude-haiku-5-5`)만 썼다. 모델을 바꾸면 달라지는지는 재지 않았다(워크플로 입력으로 바꿔 돌릴 수는 있다).
- 다음에 해 볼 것: 근거 판정의 출력 순서(이유 → 라벨) 바꾸기(4.2절), 이웃 절 확장과 낡은 문서 표시(6.4절), 청크 단위 검색 지표, 평가용 문항 추가와 사람 검수.

## 9. 실행 방법

모델을 부르지 않는 것(로컬에서 바로 실행):

```bash
python -m batondesk.evals retrieval --split test
python -m batondesk.evals baselines --split test
python -m batondesk.evals grounding --split test --rules-only
python -m batondesk.evals check-frozen
python scripts/validate_eval_data.py
python -m batondesk.evals regrade eval_results/runs/*agent-test*     # 저장된 실행을 지금 채점 기준으로 다시 채점
python -m batondesk.evals compare <A 폴더> <B 폴더>                    # 같은 문항끼리 짝지은 차이
python -m batondesk.evals failures <실행 폴더>                         # 실패한 실행의 대화와 이유
```

실제 모델을 부르는 것(GitHub Actions 의 `eval-live` 워크플로를 수동 실행. 저장소 시크릿 `ANTHROPIC_API_KEY` 필요):

| 무엇을 보려는가 | 입력 |
|---|---|
| 모델 호출이 되는지만 | suite=`smoke-only` |
| 프롬프트 버전 비교 | 같은 split·reps 로 `agent_prompt`, `grounding_prompt` 만 바꿔 두 번 실행한 뒤 `compare` |
| 판정기 정확도 | suite=`grounding` 또는 `resolution`, split=`dev`/`test`, reps=`3` |
| 모델 비교 | 같은 조건에서 `agent_model`, `judge_model` 만 바꿔 실행 |
| 데모용 상담 기록 | suite=`record-demo` |

결과는 실행의 Summary 탭, 아티팩트, `eval-runs` 브랜치의 `runs/<실행 id>/` 에 남는다(`manifest.json`, `summary.json`, `results.jsonl`, `errors.jsonl`, `trajectories.jsonl.gz`).
`scripts/import_eval_runs.sh` 가 그중 대화 전문을 뺀 네 파일을 `eval_results/runs/` 로 가져온다. 이 문서가 인용한 실행은 모두 거기에 있다(25건).
키가 있는 환경이면 같은 명령을 로컬에서도 돌릴 수 있다: `ANTHROPIC_API_KEY=… python -m batondesk.evals agent --split dev --reps 3 --label my-run`.

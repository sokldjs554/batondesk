# 설계 결정

> 모든 주문·고객·정책 데이터는 가상의 예시 쇼핑몰 "바통마켓"의 **예시 데이터**입니다.

결정마다 "무엇을 골랐고, 무엇을 버렸고, 왜"를 적는다. 표의 **상태**는 다음 뜻이다.

- **사용** — 이 저장소의 코드가 실제로 쓴다.
- **검토만** — 조사하고 비교했지만 쓰지 않았다. 경험으로 내세울 수 없다.

## 공고의 우대 기술: 쓴 것과 검토만 한 것

| 기술 | 상태 | 어디에 / 왜 |
|---|---|---|
| LangGraph (LangChain 계열) | 사용 | 에이전트 한 턴의 흐름을 상태 그래프로 구성(`src/batondesk/agent/graph.py`). 노드 8개, 조건 분기 2곳, `astream` 으로 진행 단계를 화면에 전달 |
| LangChain의 모델 래퍼·프롬프트 템플릿·체인 | 검토만 | 모델 호출은 Anthropic SDK를 직접 쓴다. 아래 D1 참고 |

| GCP Cloud Functions / Cloud Run | 검토만 | Cloud Run은 이 이미지를 그대로 올릴 수 있어 가장 현실적인 대안이다. 계정·결제 설정이 필요해 이번에는 하지 않았다 |
| AI 제품 UX | 사용 | 출처 표시, 걸러진 답을 보여 주지 않는 흐름, 인계 요약, 데이터 출처 구분 표시. 근거는 `docs/research.md` 6절. 실제 사용자 테스트는 하지 않았다 |

## D1. 그래프는 LangGraph, 모델 호출은 SDK 직접

**결정**: 한 턴의 흐름(검색 → 모델·도구 반복 → 근거 검사 → 재작성/인계)은 LangGraph `StateGraph` 로, 모델 호출은 Anthropic 파이썬 SDK로 직접 한다.

**이유**
- 분기가 코드 흐름에 묻히지 않는다. "근거 검사에 걸리면 한 번 다시 쓰게 하고, 또 걸리면 사람에게"가 그래프의 간선으로 남는다.
- 노드가 끝날 때마다 이벤트가 나와서(`astream(stream_mode="updates")`) 진행 단계를 화면에 흘려보내기 쉽다.
- 모델 호출을 직접 하는 이유: 요청마다 캐시 지점(`cache_control`), 구조화 출력(`output_config.format`), 도구의 `strict` 스키마, 응답의 실제 모델명·토큰 사용량·재시도 횟수를 그대로 다뤄야 한다. 래퍼를 한 겹 더 두면 이 값들을 꺼내는 코드가 래퍼의 버전에 묶인다.

**버린 것**: 전부 직접 짠 `while` 루프(기존 `five-whys-agent` 방식). 동작은 같지만 분기가 늘수록 읽기 어려워진다.

**대가**: `langgraph`와 `langchain-core`가 의존성으로 들어온다. 그래프 상태에 파이썬 객체(SDK 응답 원본)를 그대로 싣기 때문에 체크포인트 저장은 쓰지 않는다.

## D2. 고객에게 나가는 글은 반드시 근거 검사를 지난다

**결정**: 모델의 초안은 `verify` 노드를 통과해야 고객에게 나간다. 걸리면 고객에게 보이지 않고, 한 번 다시 쓰게 한 뒤 또 걸리면 시스템이 상담원에게 넘긴다.

**이유**: 상담에서 가장 비싼 오류는 틀린 정책 안내다. "모델이 대체로 맞다"가 아니라 "틀린 답이 나가는 경로가 없다"를 구조로 만들고 싶었다.

**대가**: 답변 턴마다 판정 호출이 한 번 더 든다(지연과 비용). 그래서 답변 글자를 스트리밍하지 않는다 — 검사 전 글자가 화면에 먼저 보이면 이 보장이 깨진다. 판정기도 틀리므로 판정기 자체를 따로 평가한다(`docs/evaluation.md`).

**설정**: `BATONDESK_GROUNDING_MODE=block|flag|off`. `flag` 는 내보내되 표시만 하고, `off` 는 검사를 끈다(비교 실험용).

## D3. 근거 검사는 두 겹: 규칙 + LLM

**결정**: (1) 답변의 금액·기간·날짜가 근거에 글자 그대로 있는지 규칙으로 대조하고, (2) LLM이 답변을 주장 단위로 나눠 주장마다 라벨을 붙인다. 최종 판정은 LLM의 한마디가 아니라 라벨을 코드가 합쳐 낸다.

**이유**: 숫자 오류는 규칙이 싸고 확실하게 잡는다. 반면 "근거의 값으로 계산해 나온 숫자"(반품 기한까지 4일)는 규칙이 오탐한다. 그래서 규칙 결과는 LLM에 단서로 넘기고, 막는 결정은 LLM 판정이 한다. LLM 판정을 쓸 수 없을 때만 규칙으로 막는다(닫힌 쪽으로 실패).

**알려진 빈틈**: 규칙만 쓰는 상황에서 "기간"(7일 → 14일)은 막지 않는다. 계산으로 나온 기간과 구분할 수 없어서다. 금액·날짜·비율·주문번호는 막는다.

## D4. 최종 응답은 "응답 제출 도구"로 받는다 (처음 결정을 실제 실행 뒤에 바꿈)

**결정**: 에이전트는 마지막에 `respond` 도구를 불러 응답을 제출한다. 인자는 strict 스키마(`action`, `message`, `citations`, `handoff_reason`, `handoff_summary`, `kb_issue`)다. 도구 없이 글만 쓰고 끝내면 그 글은 고객에게 나가지 않고 다시 요청한다(최대 2번).

**이유**: 고객에게 보이는 글과 시스템이 읽는 판단을 분리해야 인계·근거 검사·집계를 문자열 파싱 없이 코드로 처리할 수 있다.

**처음 결정과 바꾼 이유**: 처음에는 구조화 출력(JSON 출력 형식, `output_config.format`)으로 받았다. 실제 API로 처음 돌린 점검에서 두 번 중 한 번, 모델이 주문 조회 도구를 부르지 않고 `{"action":"answer","message":"",…}` 같은 빈 응답을 냈다([실행 기록](https://github.com/sokldjs554/batondesk/actions/runs/45793173101)). 공급자 문서에도 "JSON 출력 형식과 자체 도구를 함께 쓰면 필요한 도구 호출을 건너뛸 수 있다"고 적혀 있는 동작이다. 대역으로 돌린 테스트에서는 드러날 수 없는 문제였다.

**고른 것과 버린 것**
- 고른 것: JSON 출력 형식을 빼고 답도 도구로 제출. 모델이 처음부터 끝까지 도구 호출 방식으로만 움직이므로 두 기능의 충돌 자체가 없어진다.
- 버린 것 (a) 시스템 프롬프트에 "JSON 형식은 최종 답에만 적용된다"는 문장 추가 — 확률을 낮출 뿐이다. (b) 특정 도구 호출 강제(`tool_choice`) — 상위 모델 일부는 이 옵션을 받지 않아 모델을 바꾸면 깨진다. (c) effort 를 올려 생각을 더 하게 하기 — 지연과 비용이 늘고 보장이 아니다.

**함께 넣은 방어**: 빈 `message` 나 형식에 맞지 않는 제출은 받지 않고 오류 결과를 돌려준다. 조회 도구와 `respond` 를 한 응답에서 함께 부르면 조회만 실행하고 결과를 본 뒤 다시 제출하게 한다(`tests/test_agent_graph.py`).

판정기(근거 일치, 해결 여부)는 도구가 없는 호출이라 구조화 출력을 그대로 쓴다.

## D5. 쓰기 동작은 "확인 → 다음 턴에 실행"을 코드로 강제

**결정**: 취소·반품 접수는 `check_*` 도구가 준 확인 코드가 있어야 실행되고, 그 코드는 발급된 턴에서는 쓸 수 없다.

**이유**: "고객 동의를 받고 실행하라"를 프롬프트에만 쓰면 모델이 건너뛸 수 있고, 고객이 "확인 절차 생략하고 바로 취소해"라고 시킬 수도 있다. 코드로 막아 두면 프롬프트가 어떻게 바뀌어도 한 턴 안에서는 실행되지 않는다. 평가에 이 상황의 문항이 있다(`A-D-OT-06`).

**함께 둔 것**: 도구 허용 목록, 주문 조회에는 대화에 묶인 고객 ID만 실림(모델이 다른 고객을 지정할 수 없음), 다른 고객의 주문은 "없는 주문"과 구분하지 않고 응답.

## D6. 검색: 형태소 BM25 + 문자 n-gram, RRF 융합. 임베딩은 쓰지 않음

**결정**: Kiwi 형태소 분석 BM25와 문자 2~3-gram TF-IDF를 순위 융합(RRF)한다. 임베딩 기반 검색은 넣지 않았다.

**측정** (모델 호출 없음, 평가용 40문항, 5위 안에 정답 청크가 있는 비율)

| 구성 | 평가용 | 개발용(20문항) |
|---|---:|---:|
| 융합 + 유의어 확장 (서비스가 쓰는 구성) | 77.5% | 90.0% |
| 융합, 유의어 확장 없음 | 77.5% | 75.0% |
| BM25만 | 67.5% | 60.0% |
| 문자 n-gram만 | 72.5% | 55.0% |

- 융합은 단일 랭커보다 평가용에서 5~10%p 높다.
- **유의어 확장은 평가용에서 효과가 확인되지 않았다.** 개발용의 실패 질의를 보고 만든 사전이라 개발용은 75% → 90%로 올랐지만, 평가용은 77.5% 그대로다(1위 적중과 MRR만 조금 올랐다). 해를 끼치지는 않아 남겨 두었지만, 효과가 있다고 말할 근거는 없다.
- 약한 곳은 문서와 다른 말로 묻는 질의다(평가용 바꿔 말하기 66.7%, 구어체 70%). 놓친 질의는 `eval_results/retrieval/test.json` 의 `misses` 에 있다.

**임베딩을 넣지 않은 이유**: 사용 중인 LLM 공급자가 임베딩 API를 제공하지 않아 다른 공급자의 키가 하나 더 필요하고, 로컬 임베딩 모델은 무료 호스팅(512MB)에 형태소 분석기와 함께 올릴 여유가 없다. 문서 23건 규모에서는 에이전트가 검색 도구로 질의를 바꿔 다시 찾는 쪽이 먼저라고 판단했다. 그 효과(턴 안에 정답 문서를 확보한 비율)는 에이전트 평가의 `retrieval_any_hit` 로 잰다.

**메모리**: Kiwi 기본 설정은 상주 메모리를 약 510MB 쓴다. 다어절 사전과 오타 사전을 빼면 약 330MB이고, 위 검색 수치는 바뀌지 않았다. 서버 전체는 576MB → 393MB로 줄었다(로컬 측정, 규칙 엔진으로 대화 3턴 후 최대 상주 메모리).

## D7. 인계와 해결의 정의

- 인계 사유는 자유 문장이 아니라 정해진 값이다(`agent/protocol.py`). 모델이 고르는 값 9개와 시스템이 붙이는 값 2개(`ungrounded_answer`, `agent_error`)를 구분한다.
- 인계 뒤에는 AI가 답하지 않는다. 고객 메시지는 저장되어 상담원에게 보인다. 상담원이 "AI에게 돌려주기"를 하면 다시 AI가 답한다.
- 한 번이라도 인계된 대화는 AI가 해결한 것으로 세지 않는다.
- 해결률의 정의는 `docs/research.md` 3절과 `src/batondesk/obs/metrics.py` 에 있다.

## D8. 저장소는 SQLite 한 파일

대화·메시지·턴 실행 기록·인계·이벤트·비용 장부를 SQLite에 둔다. 공개 데모의 디스크는 재배포마다 초기화되므로, 시작할 때 저장된 상담 기록(`data/recordings/`)을 다시 싣는다. 여러 인스턴스로 늘리려면 PostgreSQL로 옮겨야 한다(`store/repo.py` 에 SQL이 모여 있다).

## D9. 프롬프트는 파일, 버전은 잠금

프롬프트는 `prompts/<종류>/vN.yaml` 에 두고 `prompts/LOCK.json` 에 버전별 sha256 을 적는다. 잠긴 버전의 내용이 바뀌면 CI가 실패한다 — 평가에 쓴 프롬프트를 나중에 고쳐 놓고 같은 이름으로 부르는 일을 막기 위해서다. 실행 기록에는 버전 ID와 해시가 함께 남는다. 도구 설명문도 프롬프트 버전이 덮어쓸 수 있어 버전의 일부로 본다.

## D10. 모델 선택은 평가 결과로

기본값은 `claude-haiku-5-5`(에이전트·판정 모두)다. 실시간 채팅은 지연 시간이 중요하고 공개 데모의 호출 비용을 저장소 주인이 부담하기 때문에 가장 빠르고 싼 모델에서 시작했다. 더 큰 모델과의 비교는 같은 평가 자료로 돌린 결과를 보고 정한다(`docs/evaluation.md`). 설정은 환경 변수로 바꾼다.

평가 결과: 평가용에서 턴 지연 p50 5.5초, 통과율 89.6%(재채점 92.7%)였다. 더 큰 모델과의 비교는 하지 않았다. 남은 실패의 큰 원인이 검색이라(6.4절) 모델을 키워도 풀리지 않을 것으로 보지만, 재 보지 않은 추측이다.

아래 D11~D16 은 실제 모델 실행을 보고 더하거나 바꾼 결정이다. 저장소 주인의 채택 선언(D1~D10) 뒤에 에이전트가 쓴 것이라 주인이 아직 읽고 채택하지 않았다.

## D11. 근거 판정기에는 에이전트가 본 것을 모두 준다

처음에는 판정기에 검색된 문서와 성공한 도구 결과, 대화만 줬다. 실제 실행에서 판정기는 에이전트가 알고 쓴 말을 근거 없음으로 막았다: 고객 이름, 지금 시각("오전 10시라 오늘 출고"), 형식이 틀린 주문번호에 대한 도구의 오류 문구, 상담 AI의 운영 규칙("확인 절차는 생략할 수 없습니다").

- 고른 것: (1) 상담 정보(시각, 고객 이름)를 판정 입력에 넣는다. (2) 실패한 도구 호출도 근거 묶음에 남긴다. (3) 상담 AI의 운영 규칙을 판정 프롬프트에 적는다.
- 버린 것: 판정을 느슨하게 하기("약속처럼 보이는 말은 넘어가라"). 근거 없는 약속을 잡는 것이 이 검사의 목적이라, 기준을 낮추지 않고 판정기가 볼 수 있는 것을 늘렸다.
- 원칙: 생성하는 쪽과 검증하는 쪽이 보는 정보가 다르면 검증은 틀린다.
- 남은 문제: 운영 규칙이 에이전트 프롬프트와 판정 프롬프트 두 곳에 적혀 있다. 한쪽만 고치면 어긋난다.

## D12. 검색된 공지는 전체를 준다 — 그리고 이 수정은 좁았다

문서를 절 단위로 색인하므로 한 문서의 일부만 검색될 수 있다. 개발용에서 연말 배송 공지의 "출고 시점" 절만 검색되고 "1~2영업일 더 걸린다"는 절이 빠져, 모든 프롬프트 버전에서 그 수치가 답에 없었다.

- 고른 것: 공지(`doc_type: notice`)의 한 절이 검색되면 같은 공지의 나머지 절도 근거로 준다. 검색 순위와 검색 평가는 바꾸지 않는다.
- 버린 것: 모든 문서의 이웃 절 확장(근거가 2~3배로 늘어 판정 비용과 방해 문서가 늘 것을 걱정했다), 공지를 한 청크로 색인(청크 ID가 바뀌어 동결한 평가 자료가 깨진다).
- **결과**: 평가용에서 같은 종류의 실패가 공지가 아닌 정책 문서에서 났다(`A-T-KB-09`). 한 사례에 맞춘 수정이었다. 다음에는 문서 종류와 무관한 이웃 절 확장을 새 평가 문항으로 재야 한다.

## D13. 프롬프트를 올리는 기준

- 후보는 **개발용만 보고** 고른다. 평가용은 고른 뒤에 기준선과 함께 한 번 돌린다.
- 기준선과 후보는 **같은 커밋**에서 돌린다. 코드가 다르면 프롬프트의 효과와 섞인다.
- 같은 문항끼리 짝지은 차이와 구간을 본다. 구간이 0을 포함하면 "좋아졌다"고 쓰지 않는다.
- 이번 결과: v4 는 평가용 통과율에서 v1 과 차이가 없었다. 그래도 올린 것은 지연 p95 가 15.0초 → 10.0초, 비용이 15% 줄어서다. 과잉 인계가 늘어난 것(0.9% → 3.4%)은 감수했다. 반대 선택(v1 유지)도 방어할 수 있는 결정이다.

## D14. 채점 규칙이 틀렸을 때

채점은 글자 비교 규칙이라 틀릴 수 있고, 실제로 틀렸다.

- 실패한 실행은 전부 읽는다. 채점이 틀린 것이면 규칙을 고치고 변경 기록에 남긴다.
- 평가용을 돌린 **뒤에** 고친 경우에는 고치기 전 수치를 지우지 않는다. "동결된 채점 그대로"와 "재채점"을 나란히 적는다.
- 예전 실행을 다시 돌리지 않고 지금 규칙으로 다시 채점하는 명령을 둔다(`evals regrade`). 저장된 대화에서 글자 비교만 다시 하고, 주문 상태·도구 사용은 저장된 값을 쓴다.
- 고치는 것은 금지어와 동의어뿐이다. 기대하는 행동과 정답 내용은 평가용을 본 뒤에 바꾸지 않는다.
- 판단이 갈리는 것은 고치지 않고 실패로 둔다.

## D15. 회귀 게이트는 개발용으로, 값은 낮게

프롬프트·에이전트·검색·평가 자료가 바뀐 push 마다 개발용 40문항을 2회 돌려 통과율 85%, 주입 차단 100%, 주문 상태 일치 100%를 본다.

- 개발용을 쓰는 이유: 평가용을 push 마다 돌리면 평가용에 맞춰 고치게 된다.
- 값을 낮게 잡은 이유: 같은 구성도 실행마다 86~96% 로 흔들렸다(40문항 × 2회). 기준이 높으면 고친 것이 없는데 빨간 불이 난다. 이 게이트는 "크게 깨졌는가"만 본다.
- 주입 차단과 주문 상태를 100%로 둔 이유: 틀린 답이 나가는 것과 주문이 잘못 바뀌는 것은 한 건도 허용하지 않는다. 지금까지 모든 실행에서 100%였다.

## D16. 화면 디자인을 "굵은 외곽선 + 그림자"에서 "가는 선 + 뜻이 있는 색"으로 바꾼다 (2026-11-27)

저장소 주인이 "디자인도 바꿔 달라"고 요청했고, 바꾸기 전에 사례를 조사했다(사이트 13곳, 오픈소스·개인 프로젝트 화면 10개, UX 지침, 지금 배포본의 계측). 조사 보고서는 저장소에 넣지 않았다(저장소 밖 작업 파일).

**조사에서 확인된 것(스타일까지 본 사이트 10곳 기준)**: 밝은 바탕에 따뜻한 미색 보조 면, 강조색 하나, 위쪽 가로 메뉴, 그림자 없는 12~20px 카드가 공통이었다. 굵은 외곽선과 딱딱한 그림자를 쓰는 곳은 없었다. 이전 BatonDesk 는 그 바깥에 있었다.

**지금 배포본의 문제(계측)**: 웹 글꼴을 싣지 않음(글꼴 요청 0건, 대체 글꼴에서 한글·영문이 서로 다른 글꼴로 갈림) · 글자 크기 29종 · 한 화면에 강조 색조 6~7개, 지표 카드 색은 뜻이 아니라 순서로 칠함 · 알약·배지 20종 · 모서리 15종 · 인계 알약의 글자 대비 4.14:1(기준 4.5 미달) · 모바일에서 내용 전에 177px(화면의 21%) · 평가 표의 657px 가 가려져 있는데 밀 수 있다는 표시가 없음.

- 고른 것 — 방향: 미색 바탕과 남색 글자는 그대로 두고, 굵은 외곽선과 오프셋 그림자를 걷어 1px 선으로 바꾼다. 색은 뜻이 있을 때만 쓴다: 코발트 = 고객이 한 말·링크, 라일락 = AI가 한 말, 버터 = 근거·출처, 코랄 = 보류·인계·실패, 남색 = 글자·누르는 버튼·고른 상태·사람(상담원). 숫자는 분모와 함께 가는 선으로 나눈 칸("장부")에 적는다.
- 고른 것 — 체계: Pretendard 를 웹 글꼴로 직접 싣는다(OFL, 동적 부분집합 92조각 3.1MB, 필요한 조각만 내려받음). 글자 크기 10단계, 굵기 400·600·700, 모서리 4단계, 알약 5종(분류는 선만, 상태 3색, 남색). 글자 대비는 계산해 모두 4.5:1 이상. 움직임 줄이기 설정을 따른다. 모바일은 안내 띠 한 줄 + 상표·메뉴 한 줄(내용 전 높이를 재 보니 177px → 86px).
- 고른 것 — 화면: 첫 화면에 분모가 붙은 측정 결과 칸(개선을 입증하지 못했다는 것을 포함), 빈 채팅에 시작 문의 3개, 저장 기록의 출처를 한 줄 + 펼치기로, 평가 표는 첫 열 고정과 가로 밀기 표시, 프롬프트 설명은 한 줄 45자 안팎.
- 버린 것: (a) 굵은 외곽선·그림자를 더 밀어붙이기 — 사례에 선례가 없고 "안전해야 하는 제품"에는 부담이라는 의견이 있었다(블로그 의견이라 약한 근거). (b) delight.ai 의 라임·세리프 제목을 따라가기 — 닮는 것이 목적이 아니고, 라임은 소유자의 "초록 위주 금지"에 가깝다. (c) 왼쪽 세로 메뉴 콘솔 — 소유자의 제약. (d) 다크 모드 — 범위 밖.
- 추가(채널톡 ALF 페이지에서 빌림): 제목 굵기 600·줄 높이 1.3배, 구간 제목 두 줄, AI 답은 말풍선 없이 본문 글(왼쪽 라일락 줄 + 꼬리표). 그라데이션·꽃 심벌 같은 브랜드 표시는 가져오지 않았다. AI 답의 말풍선을 없앤 효과는 확인하지 않았다.
- 추가(앱 화면 배치): 고객 화면은 대화 옆에 "AI가 한 일"을 기본으로 두고, 운영 화면은 한 문장 요약과 해결 내역 막대를 앞세우며, 상담원 화면은 인계 요약을 위로 올렸다. 상담원 화면에 왼쪽 목록 열(받은편지함형)을 두는 안은 옆 막대 금지와 부딪혀 쓰지 않았다.
- 지킨 제약: 회색·초록 위주 배색 금지, 세로 막대(옆 메뉴) 금지. 새 화면 캡처 35장에서 재 보니(채도 0.10 미만·중간 밝기 픽셀을 회색으로 센 값, 1/4로 줄인 그림) 회색은 평균 6.4%(PC 2~5%, 모바일 3~13%), 초록 색상대는 0%였다. 글자 가장자리의 흐림도 회색으로 세어져 모바일에서 높게 나온다. 처음 잰 값에서 근거 상세를 연 화면은 어두운 막 때문에 회색이 50%로 나와, 막을 남색 기운이 있는 색으로 바꿨다.
- 약점: 1배 화면에서 이미 선이 1px 이었기 때문에 "굵은 외곽선"의 인상은 사실 그림자와 색 면에서 나왔다. 그림자를 걷으면 이전의 개성 일부가 사라진다. 남긴 것은 제목 아래 세 색 밑줄과 상표의 바통 막대뿐이다. 이것이 "관습에 묻힘"이 될지는 보는 사람의 판단이다.
- **확인하지 않은 것**: 실제 사용자나 디자이너가 새 화면을 평가한 적이 없다. Windows·macOS 의 기본 글꼴에서 어떻게 보이는지는 Pretendard 를 싣기 때문에 같다고 추정하지만 그 환경에서 열어 보지는 않았다. 이 결정은 에이전트가 쓴 것으로, 주인이 아직 채택하지 않았다.

# 이 저장소가 만들어진 방식 — 누가 무엇을 했나

> 모든 주문·고객·정책 데이터는 가상의 예시 쇼핑몰 "바통마켓"의 **예시 데이터**입니다.

이 문서는 지원 서류를 쓸 때 사실과 다르게 쓰지 않도록, 실제로 일어난 일만 적는다.
자기소개서나 포트폴리오 문장은 여기 없다.

## 한 줄 요약

요청서 한 건을 받아 **AI 코딩 에이전트(Claude Code)가 조사·설계·구현·테스트·문서화를 수행했다.**
저장소 주인은 요청서를 쓰고, 저장소를 만들고, 키를 시크릿에 넣었다. **주인이 코드를 직접 쓰거나 결과를 검토·재현한 기록은 아직 없다.**

요청서의 표현은 "Codex 전달 메시지"였지만 실제로 작업한 도구는 Claude Code다. 서류에 도구 이름을 쓸 때 주의한다.

## 1. 저장소 주인이 직접 한 일

| 한 일 | 근거 |
|---|---|
| 요청서 작성: 공고 분석, 새 저장소로 진행한다는 판단, 상담 흐름 7단계, 평가해야 할 상황 8가지, 평가 원칙(개발용·평가용 분리, 반복 실행, 자동 평가와 사람 검수 구분, 비용·지연 제시 조건), 디자인 제약, 제출 자료 목록 | 세션의 첫 메시지 |
| 새 GitHub 저장소 `sokldjs554/batondesk` 생성 | 세션 중 "만들었어 추가도 했고" |
| Claude API 키를 저장소의 Actions 시크릿으로 등록(주인의 말에 따름. 에이전트는 시크릿의 존재를 확인할 수 없다) | 같은 메시지 |
| 세션 환경 생성 승인, 키 입력 방식 결정(환경 변수 대신 GitHub 시크릿) | 세션 중 승인과 "github 시크릿에 추가해줄게" |

요청서에 담긴 판단(무엇을 평가할지, 무엇을 만들어 내지 말지)은 주인의 것이다. 아래의 설계·구현 결정은 에이전트가 내렸고, 주인이 검토한 뒤에야 주인의 결정이 된다.

## 2. AI 에이전트(Claude Code)가 한 일

| 영역 | 내용 |
|---|---|
| 조사 | 공고 원문 재확인과 구분, 기존 저장소 13개 조사, 국내외 상담 제품 조사(검색 기반), 관련 논문 확인 |
| 설계 결정 | 업무 선택(전자상거래 상담), 프로젝트 이름, 구조, LangGraph 사용과 모델 래퍼 미사용, 근거 검사 2겹, 답변 스트리밍 안 함, 쓰기 전 확인 코드, 검색 구성, 지표 정의, 모델 기본값, 화면 구성과 배색 — `docs/design-decisions.md` |
| 구현 | `src/batondesk/` 전체, 지식 문서 23건, 예시 주문 데이터, 프롬프트 3종, 화면 5개와 위젯 |
| 평가 준비 | 평가 자료 284문항(에이전트 104, 근거 판정 64, 해결 판정 56, 검색 60)과 정답 라벨, 채점기, 실행기, 통계, 검증 스크립트 |
| 측정 | 검색 품질, 무행동 기준선, 규칙 검사 단독 성능, 서버 메모리 — 모두 모델 호출 없는 측정 |
| 테스트 | 단위·통합 테스트 132건, 브라우저 화면 점검 118항목(PC·모바일) |
| 운영 준비 | CI 워크플로, 실제 모델 평가 워크플로, Dockerfile, Render 설정 — 작성만 했고 실행되지 않았다 |
| 문서 | 이 저장소의 모든 문서 |

작업 방식: 주 에이전트가 설계와 핵심 코드를 쓰고, 독립된 일(기존 저장소 조사, 제품 조사, 화면 구현, 판정기용 평가 자료 작성)은 하위 에이전트에게 맡긴 뒤 결과를 검토해 반영했다. 모든 커밋에 `Co-Authored-By: Claude` 가 붙어 있다.

에이전트가 **하지 못한 것**은 `docs/limitations.md` 의 첫 절에 있다(실제 모델 호출, CI 실행, 배포).

## 3. 저장소 주인이 검토·재현한 일

**아직 없다.** 아래를 직접 해 본 뒤 날짜와 결과를 적으면 "검토·재현했다"고 말할 수 있다.
해 보지 않은 항목을 한 것처럼 쓰지 않는다.

### 재현 체크리스트

| # | 할 일 | 방법 | 확인할 것 | 한 날짜 / 결과 |
|---|---|---|---|---|
| 1 | 로컬 테스트 재현 | `pip install -e ".[dev]" && pytest` | 132건 통과 | |
| 2 | 화면을 직접 써 보기 | `BATONDESK_LLM_MODE=scripted batondesk serve` 후 `/chat` → `/desk` → `/ops` | 상담원 연결 → 상담원 화면에서 답장 → 고객 화면에 표시되는 흐름 | |
| 3 | 모델 호출 점검 | Actions → `eval-live` → suite=`smoke-only` | 초록 불, Summary의 호출 기록 | |
| 4 | 개발용 에이전트 평가 | `eval-live` → suite=`agent`, split=`dev`, reps=`3` | 통과율과 실패 문항. **실패 문항 5개 이상을 직접 읽고** 모델의 잘못인지 채점의 잘못인지 판단 | |
| 5 | 평가용 라벨 검수 | `data/evals/agent/test.jsonl` 등에서 문항을 골라 `note` 와 지식 문서를 대조 | 라벨에 동의하지 않는 문항이 있는지. 검수한 문항 수를 적는다 | |
| 6 | 판정기 평가 | `eval-live` → suite=`judges`, split=`both`, reps=`3` | 놓친 문항·잘못 막은 문항 목록을 읽어 보기 | |
| 7 | 프롬프트 개선 한 바퀴 | 4번의 실패를 보고 `prompts/agent/v2.yaml` 작성 → 개발용 비교 → 평가용 비교 | 같은 문항에서의 차이와 나빠진 문항 | |
| 8 | 배포 | Render에서 저장소를 Blueprint로 연결, `ANTHROPIC_API_KEY` 입력 | 공개 주소의 `/v1/release` 가 보여 주는 커밋 | |
| 9 | 코드 읽기 | `agent/graph.py`, `checks/grounding.py`, `tools/executor.py`, `evals/graders.py` | 면접에서 한 줄씩 설명할 수 있는지 | |

4·6·7번을 하면 `docs/evaluation.md` 의 빈칸을 실측값으로 채워야 한다.

## 4. 서류에 쓸 때 지킬 것

- "내가 구현했다"가 아니라 "AI 에이전트에게 요구사항과 평가 원칙을 주고 구현하게 했다"가 사실이다. 직접 한 것은 1절뿐이다.
- 3절의 체크리스트를 수행한 항목만 "검토했다 / 재현했다"고 쓴다.
- 없는 숫자를 쓰지 않는다: 답변 정확도, 해결률, 환각 탐지율, 응답 시간, 비용은 실행하기 전까지 없다.
- "사람 검수", "사용자 평가", "실서비스 운영", "팀 협업"은 하지 않았다.
- 검색 수치를 쓸 때는 조건을 함께 쓴다: 평가용 40문항, 5위 내 적중 77.5%, AI가 쓴 질의, 유의어 확장의 효과는 확인되지 않음.
- 벤더 제품에 대한 설명은 원문을 직접 확인한 뒤에 쓴다(`docs/research.md` 의 확인 수준 표시).
